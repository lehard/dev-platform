# Verification: harden managed parallel task start recovery

## Completeness

- Requirement "Managed-start mutation is guarded by a persisted per-change transaction": implemented via `managed_start_transaction` (`template/scripts/start_managed_task.py`), a `contextmanager` that writes the transaction record with `atomic_write_text` *before* yielding control to the caller's body (not only at context exit), keyed and locked per managed change via the existing `locked_json` flock helper (`.managed-start-transactions/<change>.json` under the machine-local worktrees root). It is retired (`path.unlink`) only when the `with` block exits without an exception, i.e. only after the enclosing `start_managed_task` call actually completes. Covered by `test_transaction_precedes_workspace_mutation_and_retires_on_success` and `test_interrupted_start_keeps_retry_receipt` (`tests/managed_start_transaction_cases.py`).
- Requirement "Incomplete managed-start recovery is fenced to exact task identity": implemented via `recover_incomplete_managed_start`, which reasons only from the transaction's own recorded `worktree`/`branch`, and fails closed on: unique commits vs `main` (`_branch_has_no_unique_commits`), unrelated dirty paths (`_dirty_paths` + `_partial_path_is_owned`), mismatched task-local state (`read_task_state` source_issue/change comparison), an ambiguous board match (`_board_item_for_identity` raises on >1 match), and a candidate path that is not an exact registered Git worktree (`_registered_worktrees`, from `git worktree list --porcelain`). No code path scans for or removes worktrees/board entries beyond the one named by the transaction — confirmed by inspection (no glob over the worktrees root, no board scan beyond the exact `(worktree, branch)` filter). Covered by `test_recovery_preserves_unrelated_dirty_worktree`, `test_board_lookup_is_fenced_to_exact_task_identity`, and `test_unregistered_path_is_never_deleted_as_retry_debris`.
- The process-friction issue this closes (`lehard/dev-platform#262`) was read directly and maps 1:1 onto this change: task `#43`'s start being blocked/misclassified by unrelated task `#44`'s stale board/worktree state is exactly the scenario `test_recovery_preserves_unrelated_dirty_worktree` and `test_board_lookup_is_fenced_to_exact_task_identity` reproduce and fix.

## Correctness

- The transaction's identity-mismatch guard (`expected` dict compared field-for-field against `data`) fires before any mutation on a retry whose freshly-discovered package no longer matches the recorded transaction (e.g. a differently-revised package under the same change name), rather than silently reusing stale identity.
- Recovery's ordering matters and is deliberate: it checks "does anything exist at all" first (nothing to recover → proceed to fresh start), then "is this a canonical resume" (handled earlier in `start_managed_task`, not recovery), then proves ownership (registered worktree, matching task state, matching branch) *before* checking safety (no unique commits, no unrelated dirty paths) *before* checking the board — so an unprovable-ownership path is rejected before any inspection of its contents, and a provably-owned-but-unsafe path is rejected before any board mutation is attempted.
- `.resolve()` is applied consistently to every worktree path used for identity comparison (`managed_start_transaction`, `_registered_worktrees`, `_board_item_for_identity`, `recover_incomplete_managed_start`, and the multi-agent branch of `start_managed_task`), matching the realpath form `git worktree list --porcelain` itself returns. Two pre-existing tests in `tests/test_managed_task.py` (`test_managed_start_reuses_existing_worktree_only_with_matching_provenance`, `test_managed_resume_rechecks_wait_then_restores_in_progress_without_reimport`) constructed their expected `task_root` from `tempfile.TemporaryDirectory()` without resolving it; on macOS, where `TMPDIR` resolves through a `/var/folders` → `/private/var/folders` symlink, this produced a real, deterministic local failure once the transaction path started calling `.resolve()`. This was found by running the full suite locally (the original PR's CI ran on Linux, which has no such symlink, so it never surfaced there) and fixed by resolving the tests' comparison values to match the implementation's realpath convention, not by removing `.resolve()` from the implementation (which is required for correct matching against `git worktree list` output).
- `ManagedAdmissionWait` (an expected, resumable non-error state) propagates out of the `managed_start_transaction` context manager without marking the transaction complete, so the transaction/worktree are correctly preserved across a WAIT→retry→RUN sequence; `test_managed_resume_rechecks_wait_then_restores_in_progress_without_reimport` exercises this end-to-end and passes.
- The single-worktree (non-multi-agent) start path and the genuine-resume path (`_resume_existing_managed_task`) are unchanged in behavior — they were extracted from the prior inline implementation, not rewritten — confirmed by diff inspection against the pre-change version.
