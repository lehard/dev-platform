# Design: Shared Requirement integration

## Boundary

Each child retains its own managed Issue, exact OpenSpec package, isolated worktree, source commit and truthful verification receipt. A new ready-for-integration receipt is nonterminal: it binds the child Issue, change, exact committed head, and the archived contract, completed tasks, successful automated checks and verification receipt at that head. A digest of a local JSON file alone is not verification: the handoff must check the tracked archive content and the managed task identity, and assembly must recheck the live child branch head. It does not close the Issue or set Project Done.

The requirement-level integration worktree is created through guarded worktree coordination under the configured worktree root and main branch. It records an exact ordered list of child heads and the main base. An independent child's exact delta is `base..head` and must not overlap preceding independent changes. A child based on the immediately preceding ready child may use `previous-head..head`, permitting deliberate sequential edits to the same path while preserving the prior child's commit in ancestry. The manifest binds each delta base. The candidate applies those exact tree changes in order without rewriting source history or force pushing, and runs interaction checks plus the protected full validation set. The candidate's branch and worktree are single-owner: an occupied path, unexpected branch head, dirty partial application, or changed manifest stops instead of being cleaned up. Committed child-application trailers permit a retry after an interrupted run. It needs an explicit publication identity that the existing PR primitive can validate without pretending the candidate is one child; the integration manifest is the provenance source for that mode. The existing PR publication primitive owns the single final merge and exact-head reconciliation. Only after that merge may the contributing children and parent be projected as terminal.

Managed child start can accept an exact ready predecessor receipt. After the ordinary helper creates a clean isolated worktree and before it imports the new package, it fast-forwards that new branch to the verified predecessor head. The predecessor's worktree and branch are never modified. The new task records the dependency identity in its local start transaction; retry must prove the same predecessor or refuse. Scope admission may still block a genuine overlap with another active writer; no broad automatic acknowledgment is inferred from the dependency alone.

The explicit shared-candidate publisher runs from the candidate worktree, rechecks the committed manifest and all source receipts, executes the platform's full validation commands, and invokes the existing `project_publish.py` protected-PR primitive. It does not route through single-child `finish_task.py`, whose managed checkout identity is intentionally not the combined candidate's identity. On retry it discovers the exact branch-head PR; terminal child Project reconciliation occurs only after GitHub reports that exact head `MERGED` and local main fast-forward reconciliation succeeds. The parent's terminal board projection is owned by the separate derived-board-state intent, which must also prove that every ready handoff was materialized; this helper must not mark the parent Done merely because the currently linked subset is Done.

An independently published linked child uses the unchanged single-child protected path only when its archived `verification.md` contains one explicit `Requirement-Integration-Exception: <reason>` line. The publication preflight reads the source Issue's exact `Requirement:` backlink and fails closed without that committed reason. This is an auditable exception on the child's canonical OpenSpec receipt, not a parallel requirement status ledger. Standalone managed tasks have no backlink and are unaffected.

This change bootstraps the shared primitive and must publish independently once with the recorded rollout reason: the shared publisher is not yet available on `main` for its own delivery. Its representative local/bare two-child CLI rehearsal and tests verify assembly and recovery. The first real GitHub two-child shared publication is part of the later terminal Requirement execution child and remains an explicit parent acceptance gate; it is not claimed by this bootstrap receipt.

## Failure and recovery

Stale child heads, changed main, overlapping edits, missing receipts, or a failed combined check stop before publication with actionable evidence. An interrupted run reobserves the exact integration branch and PR; it never deletes, resets or takes over another agent's worktree. A separately deliverable child may use the old publication route only with an explicit recorded reason.

## Risks

The existing child finish path assumes one Issue maps to one PR. Introduce the nonterminal handoff and combined finalization behind a separate mode while preserving the old route. Tests must cover squash-merge provenance and remote-merged/local-pending recovery before using this path for real work.
