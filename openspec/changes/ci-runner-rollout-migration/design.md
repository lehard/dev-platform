## Context

- `rollout_project.apply_rollout` already works on an ephemeral branch `rollout_branch(version)` created from `origin/<base>`. Nothing reaches the protected default branch unless the rollout PR is later merged, so "stop before the protected branch changes" means: raise `ValueError` from the rollout (reported as `Managed rollout: BLOCKED`, exit 2) before any commit that would be published.
- `copier update --defaults` reads recorded answers; an absent `ci_runner` takes the default `github-hosted`. Copier replays the downstream diff against the *old* template render, so a hand-edited `runs-on` conflicts with the new render that adds a repair step.
- `platform_doctor` is the authority for label validity and for runner/answer agreement. It must stay as is.
- Workflows `dev-platform.yml` and `process-health-labels.yml` are platform-owned in both harness modes (they are not in `ALWAYS_PROJECT_OWNED_ROLLOUT_PATHS` or `PROJECT_HARNESS_ROLLOUT_PATHS`).

## Decisions

1. **Revert-then-update instead of widening recopy.** For a provable pure-runner customization the rollout restores the two `runs-on` lines to the baseline and records the answers in one rollout-branch commit, then runs the existing `copier update`. The file now equals the old render, so Copier replays no downstream diff and writes the new render (runner from the answer, repair step) cleanly. No `.rej` appears, no recopy is needed, and the path is identical for `harness_mode=platform` and `harness_mode=project`. The guarded-recopy gating and ownership sets are untouched.
2. **Proof of a pure runner customization.** For each present job file whose `runs-on` is not `ubuntu-latest`: replace the value on the matched `runs-on:` line with `ubuntu-latest` and require the file fingerprint to equal the old template's render with the project's recorded answers (`rendered_template_fingerprints(current_tag, ..., baseline_equivalence=True)`, same normalization already allowed for the platform workflow). Any other difference means other edits exist; the migration is not proven and the rollout stops.
3. **Accepted runner values.** Only what `platform_doctor` can accept back: a plain scalar label or a flow/JSON list of plain/quoted scalar labels, each matching `[A-Za-z0-9._-]+`, no duplicates. The label rule is one function shared with the doctor's check so the rollout cannot record answers the doctor would reject. The parsed labels must be identical, in order, across all present jobs. `ubuntu-latest` in every present job (or both jobs absent) is the default answer and needs no migration; a mix of `ubuntu-latest` and a custom runner is "disagreeing jobs" and stops.
4. **Stop message contract.** The error names the repository (`--repository`), the file, what was found (the `runs-on` text or the extra difference) and one next action: move the hand edit out of the platform-owned workflow (or re-express it as `ci_runner`/`ci_runner_labels` in `.copier-answers.yml` with the file otherwise equal to the baseline) and rerun the rollout. No file is left modified on the rollout branch beyond what the failed run created; the branch is ephemeral and the default branch is untouched. The migration check runs before `copier update`, so a stop never leaves a half-updated tree.
5. **Applicability.** The preflight runs only when all of: target template defines `ci_runner` (read from the target tag's `copier.yml`, so older targets are unchanged); the project's `.copier-answers.yml` has no `ci_runner`; `scm_provider` is not `gitlab`. Otherwise behavior is exactly today's. A project without hand edits (all `ubuntu-latest`) takes the unchanged path and needs no new manual action.
6. **Answers recording.** The rollout appends `ci_runner: self-hosted` and `ci_runner_labels: <comma-joined labels>` to `.copier-answers.yml` using the existing answers-file conventions, then commits answers plus the two restored workflows in a `chore:` commit before `copier update`. Copier requires a clean tree, which is why the preflight is committed rather than left in the working tree. The final rollout commit remains the update commit.
7. **One label rule across Copier and doctor.** The Copier validator for `ci_runner_labels` is expressed in Jinja as the same predicate (split on `,`, trim, every entry non-empty and matching the character class, no duplicate). A test runs a table of values (`a,,b`, `self hosted`, ` a , b `, `a,a`, trailing comma, `a!`, `[a]`, valid lists) through both the real Copier validator and `platform_doctor`'s check and requires identical accept/reject, so the two cannot drift silently. The doctor message remains the stronger, more specific one.
8. **GitLab.** `ci_runner` gets `when: "{{ scm_provider == 'github' }}"` and `ci_runner_labels` `when: "{{ scm_provider == 'github' and ci_runner == 'self-hosted' }}"`. `scm_provider` is declared before them already. A test renders a GitLab project and asserts no `ci_runner` question prompt and no recorded answer, and that rendering still succeeds because the question keeps its default. The doctor's GitLab skip is unchanged.
9. **Docs.** `docs/managed-rollout.md` "Downstream CI runner selection" is rewritten for the migration path: what is migrated automatically, what stops and why, how the message reads, and how to proceed after a stop. The old instruction to record answers first is replaced.

## Rejected alternatives

- Widen guarded recopy to `harness_mode=project` or accept a "mostly equal" file: recopy overwrites whole templates and is deliberately limited; the runner file is safe only because of a narrow proof, and the revert-then-update path needs no recopy at all.
- Write only the answers and leave the hand edit for Copier to merge: leaves `.rej` (verified) because the new render also changed the neighbouring lines.
- Leave the default answer and let CI fail, or silently set `github-hosted`: the exact outcome the Requirement forbids.
- Auto-detect arbitrary runner configurations (expressions, groups, `labels:` mappings): out of scope; those stop with a named next action.
- A Python-side Copier hook or tasks to validate labels: `--skip-tasks` is used in rollout, and a Jinja validator is the supported place for a question rule.
- Share code between Jinja and Python: not possible; a parity test is the enforceable alternative.

## Risks and mitigations

- *Restored `runs-on` lines hide a real difference.* The proof requires byte equality with the baseline render after restoring only the value; anything else stops.
- *Parity drift between the Jinja validator and doctor.* The table test fails on divergence in either direction.
- *`when`-skipped GitLab questions still change rendered output.* The test compares a GitLab render before and after, and workflows are excluded from GitLab renders already.
- *A target that lacks `ci_runner` is affected.* Applicability is decided from the target tag's `copier.yml`; a test targets an older render and asserts no preflight, no commit, no answers change.
- *The rollout branch carries two commits.* The first is a documented migration commit; the PR still reflects the net change and the doctor passes on the final head.
