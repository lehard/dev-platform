## Context

Four observation points of the publication-queue contour behave contrary to the accepted `publication-queue` spec and to the repository no-fallback rule. All evidence below was read from `main` at `bd7f234`; `template/scripts/*` is the real implementation and `scripts/*` are shims.

**Comment history.** `publication_queue._comments` calls `_gh(root, "api", f"repos/{repo}/issues/{number}/comments?per_page=100")`, raises `QueueError("PR queue comments are unavailable or exceed the bounded page")` when `len(rows) >= 100`, and returns `[row for row in rows if isinstance(row, dict)]`, silently dropping malformed rows. `_transition` documents that comments must not "grow the bounded comment page". `_events`, `_derive`, `_latest`, `_transition`, `admit`, `_integrate` and the worker all consume this one reader. `private_lineage._comments` already shows the target shape (`--paginate --slurp`, array-of-arrays validation); `lifecycle_workers.comments_for` uses `--paginate` without `--slurp` and is a separate reader reported below, not changed here.

**Check observation.** `publication_state.required_check_state_for_ref` runs `gh pr view --json state,headRefOid` (head must equal `expected_head`), then `gh pr checks --required --json name,state,workflow,link` and returns a cause-less `RequiredCheckState("unknown", ...)` for any non-zero exit. The head is verified only before the checks call, so a push between the two calls is not detected. With `--required`, a base without required checks yields exit 1 and no JSON, so a contribution PR to the unprotected Requirement integration branch is never observable as passed. Consumers map `unknown` differently: `publication_queue._integrate` raises `QueueError("required check state is unknown: ...")`, which the outer handler turns into `_block` (terminal); `candidate_lifecycle.derive_candidate` treats a non-passed snapshot as `blocked-retryable`; `project_publish.wait_for_pr_checks` fails closed but resumable; `finish_task` only resumes for pending/passed/not_registered; `rollout_preflight` maps `unknown` to BLOCKED; `publication_state` bucket logic reads `failed` vs everything else. (The original draft assumed gh exits 8/1 with JSON for pending/failed; the task 2.1 probe disproved that, see D2.)

**Trust configuration.** `publication_queue.trusted_apps` builds names from `DEV_PLATFORM_COORDINATOR_APP` plus `[publication] coordinator_app` from `read_platform_config` and `read_operator_config`, each reader wrapped in `try: ... except Exception: continue`, and ignores a non-table `[publication]` or non-string value. A malformed `.dev-platform.toml`, an operator config that was requested but is missing/invalid (`read_operator_config` raises `RuntimeError`), or a wrong type silently removes the App from the trusted set, so genuine coordinator records are ignored and queue/lifecycle state is derived from a narrowed view. `trusted_writers` already fails closed and is the model.

**Managed provenance.** `publication_queue._admission_handoff(root, branch, head)` (used by `admit` when no developer `handoff` is supplied, i.e. the legacy `project_publish` path and the `admit` CLI) proves task content only when `git rev-parse HEAD` equals the admitted head, then calls `agent_friction.current_task_content`, which is explicitly "best-effort" and swallows every exception (unreadable `.managed-task-state.json`, `content_identity` failure, a `None` proof when `merge-base` fails). Any failure, a checkout at another head, or an `OSError` returns `{"task_identity": {"branch": branch, "head": head}, "gates": {}}` -- the quick-task identity -- for a candidate that is actually managed. `_archived_verification_gate` also catches `Exception` around `managed_task.read_task_state` and malformed evidence JSON and returns `{}`. The managed-task state file is gitignored (`.gitignore: .managed-task-state.json`), so it is only visible in the task's own checkout. `candidate_lifecycle.validate_marker` accepts any non-empty dict or string identity, so nothing downstream rejects a downgraded identity.

## Goals

- One complete, ordered, validated comment-history observation; failure is named and never partial.
- Required-check observation that depends on gh JSON and head binding, not on exit-status folklore, and whose result is classified so callers can tell "wait", "repair", "retry observation" and "contract violation" apart.
- Trust sources whose failure is visible.
- Managed admission that either carries exact task-content provenance or fails, never an identity of lower assurance.
- Preserve marker authentication, exact-head ownership rules and the genuine quick-task contract.

## Decisions

### D1. Comment history

`_comments` uses `_gh(root, "api", "--paginate", "--slurp", f"repos/{repo}/issues/{number}/comments?per_page=100")`, going through the existing authenticated `_gh` entrypoint (reads retry only on classified transient failures; no other strategy). The result must be a non-empty list of page lists; every row must be a JSON object with an integer (non-bool) `id`; ids must be strictly increasing across the flattened sequence (API order, and a duplicate or regression indicates a page shifted mid-read). A valid empty history is `[[]]` and returns `[]`; an empty/`null` body or zero pages is an error, not an empty history. All validation completes before anything is returned, so a malformed later page rejects the whole observation. Every failure is raised as `QueueError("PR comment-history acquisition failed for #N: <cause>")`, naming the cause (transport text, invalid JSON, non-array outer value, non-array page, non-object row, missing/non-int id, order violation). The `per_page` ceiling and the first-page length check disappear. `_transition`'s comment about the bounded page is updated, and the existing dedupe of unchanged transitions stays (it is still correct, only its stated reason changes).

Rejected: loop with `page=N` in Python (more code, more partial-read states); keeping the ceiling as a configurable limit (still masks a valid history); dropping malformed rows (silently erases possible claims).

### D2. Check observation

Task 2.1 probe (gh 2.97.0, recorded by the executor, supervisor-reviewed) replaced the original exit-code premise: with `--json`, `gh pr checks` exits 0 with a valid JSON list for passed, pending (IN_PROGRESS) and, per gh's `--json` early return, failed checks; exit 8 only occurs without `--json`; with `--required` and no required checks on the base branch it prints "no required checks reported on the '<branch>' branch" to stderr and exits 1 with no JSON. The real defects are therefore: `unknown` carries no cause, `_integrate` blocks terminally on any `unknown`, the head is not re-read after the checks call, and the no-required-checks case is an unusable observation. The last one is a release blocker for Requirement contributions: a contribution PR targets the unprotected `requirement/BR-<n>` integration branch, so `--required` always exits 1 and the contribution can never record a passed `required-checks` gate.

`RequiredCheckState` gains `cause: str = ""`. `kind` stays one of `passed`, `pending`, `failed`, `not_registered`, `unknown`; `unknown` always carries a `cause` in `{"transport", "malformed", "head-mismatch", "unsupported-state"}` and a detail. One shared classification path serves `required_check_state` and `required_check_state_for_ref`:

1. `gh pr view` (state, head, base) non-zero -> `unknown`/`transport`; invalid JSON/shape -> `unknown`/`malformed`; head differs from `expected_head` -> `unknown`/`head-mismatch`.
2. Resolve the required set from the PR's final protected target. For a base of `main` (the configured main branch) use `gh pr checks <ref> --required --json name,state,workflow,link`. For a base matching the Requirement integration branch pattern `requirement/BR-<n>`, read the configured main branch's required status checks (`gh api repos/{repo}/branches/{main}`: `protection.required_status_checks.contexts` and `protection.required_status_checks.checks[].context`), run `gh pr checks <ref> --json name,state,workflow,link` (no `--required`), and keep only rows whose `name` is a required context; preserve `checks[].app_id` bindings (null or -1 means any App), resolving bound checks through paginated exact-head check runs with matching `app.id`, using the newest run per name and App; a required context with no row is `PENDING` (not yet registered on this head). Any other base is unsupported and raises a named error (no guessing).
3. `gh pr checks` exit 0 with a valid JSON list -> classify with the existing `_classify_required_checks` (empty -> `not_registered`, any failed -> `failed`, all passed -> `passed`, passed/pending -> `pending`, otherwise `unknown`/`unsupported-state`). Exit 0 with invalid JSON/shape -> `unknown`/`malformed`.
4. `--required` exit 1 with empty stdout (the no-required-checks condition) is resolved without parsing CLI wording: read the base branch's required status checks through the API; a valid branch response with `protected: false` or an empty required set -> `not_registered` with detail naming the base; a non-empty required set -> `unknown`/`malformed` (gh reported none while the base requires checks); an API failure -> `unknown`/`transport`. Any other non-zero exit, or exit 1 with non-empty stdout -> `unknown`/`transport` with the gh diagnostic.
4a. In contribution mode (`gh pr checks --json` without `--required`), exit 1 with empty stdout is what gh returns before any check has registered on the head; gh offers no structured way to distinguish it from a transport failure without parsing its wording, so it is classified `unknown`/`transport`. `_integrate` maps that cause to a non-terminal `waiting` result, so the candidate is re-observed once checks register and is never blocked by it.
5. After the checks call `gh pr view` is read again and must still equal `expected_head`; otherwise `unknown`/`head-mismatch` (gh has no head parameter for `pr checks`).

The branch reader uses the Get a branch endpoint, which requires Contents read (already granted to the coordinator), rather than the Administration-read protection endpoint. It validates the branch name, boolean `protected`, and the protected branch's required-check structure. Missing branches, denied requests and malformed responses remain unusable observations; no alternate endpoint or credential is tried.

Caller mapping:

- `publication_queue._integrate`: `passed` proceeds; `pending` keeps polling then returns the existing non-terminal `waiting` ("required CI pending"); `failed` raises `IntegrationRepairNeeded(gate="required-checks")`; `not_registered` blocks as today (a main-targeted PR whose protected base requires nothing is a real configuration problem); `unknown` with cause `head-mismatch` or `transport` returns a released non-terminal `waiting` result whose reason names the cause; `unknown` with cause `malformed` or `unsupported-state` raises `QueueError` (visible block).
- `publication_queue.candidate_status` (the developer/contribution observer that currently parses exit 0/1/8 itself) uses the same shared classifier so contribution `required-checks` gates are derived from main's required set.
- `candidate_lifecycle.derive_candidate`: unchanged (`blocked-retryable` for non-passed snapshots, mismatched head ignored); a test pins that pending and failed snapshots map as before.
- `project_publish.wait_for_pr_checks`, `finish_task`, `rollout_preflight`, `publication_state` buckets: no behavior change beyond receiving causes; tests pin the recorded real gh shapes.

Rejected: classifying from stderr wording; inventing exit-code/classification agreement rules gh does not provide; treating a contribution's unprotected integration branch as "no checks required" (that would merge unchecked code into the composed candidate); returning a synthetic `pending` for transport faults.

### D3. Trust configuration fails closed

`trusted_apps` stops catching exceptions. Each source is read under its own contract and any failure is raised as `QueueError("trust source <name> is unreadable or invalid: <cause>")` naming `DEV_PLATFORM_COORDINATOR_APP`, the platform config (`.dev-platform.toml`) or the operator config. Legitimately absent sources stay valid and are explicit in the contract: unset/empty env var; no `.dev-platform.toml`; operator config not enabled (`read_operator_config` returns `{}`); no `[publication]` table or no `coordinator_app` key. Present-but-wrong values are errors: `[publication]` that is not a table, `coordinator_app` that is not a string, an operator config that is enabled but missing/invalid TOML (`read_operator_config` already raises), a `.dev-platform.toml` that fails to parse. An empty trusted set remains a possible, explicit result (nothing configured), as today.

Callers that already run inside `QueueError` boundaries (`admit`, worker, `candidate_status`) surface the message; `lifecycle_workers._coordinator_trust` and the integration/review contours call `trusted_apps` directly, so a trust failure now stops those jobs visibly instead of narrowing trust. The tests prove one caller from each family fails rather than continues.

### D4. Managed provenance at admission

`_admission_handoff` is rewritten to decide managed versus quick from authoritative state before choosing an identity, and to read proof strictly:

- Managed predicate: the checkout's managed-task state file is present (`managed_task.read_task_state(root)` returns state; a read error is raised, not ignored), or the exact head touches `openspec/changes/` (listed from git at the admitted head, not the working tree; a git failure is raised). A candidate with neither is a genuine quick task and keeps today's `{"branch","head"}` identity.
- Before any admission comment or label mutation, resolve the handoff and validate managed provenance.
- Managed requirements: verify that the named active package or a unique archived package exists; the local checkout must be at the admitted head, and `task_content_identity.content_identity(root, change)` must return a proof with a non-empty digest. Any shortfall (state unreadable, change missing, checkout at another head, `merge-base` failure producing `None`, no digest) raises `QueueError("managed candidate <branch> lacks valid exact task-content provenance: <cause>")`. There is no branch/head downgrade and no call to the best-effort `agent_friction.current_task_content`.
- `_archived_verification_gate`: absence of archived evidence still yields no gate (admission claims nothing it cannot bind); unreadable evidence, malformed JSON, or malformed gate fields now raise `QueueError` naming the evidence path; an error from `read_task_state` propagates. A satisfied gate is never fabricated.
- Archived evidence must have an outcome of `success` or `failure`, a managed-checkout object, a task-content object with a SHA-256 hex digest, and a checkout head with a 40-character Git SHA. Validate these fields even for unsuccessful evidence; only structurally valid unsuccessful evidence yields no gate.
- `rev-parse HEAD` failure raises instead of becoming an empty head.
- `_integrate` keeps the carry-forward semantics; the implementer audits that the `{"branch","head"}` placeholder identity passed to the `integrating` transition cannot replace a recorded managed identity (it inherits unless the caller proves a fresh identity). If the audit finds a reachable downgrade, design and tests are updated first.

Requirement composition admission retains its separate exact-head provenance contract: `require_composition_finalized` validates the recorded composition identity and final gates in a disposable checkout at the admitted head and returns that identity and gates for admission. It does not require single-child managed task state in the coordinator checkout. Failure of composition validation stops admission before mutations.

Supplied developer handoffs (`handoff=` with `task_identity`/`gates`) already carry validated managed identity and are unchanged.

## Risks

- Whole-history memory grows with comment count; whole-history replay is already required for marker provenance.
- Strict increasing-id validation could reject an unusual but legal API response; the tests encode GitHub's ascending order and the error names the offending ids. A comment deleted between page fetches cannot be detected and still yields a valid-looking history; this is inherent to non-atomic pagination and is the same exposure as before for one page.
- Waiting on `transport` or `head-mismatch` can repeat indefinitely during a long GitHub outage; this is intentional (non-terminal, named, visible) and bounded by coordinator cadence, but operators see it only through status reasons.
- The managed predicate (b), "head touches `openspec/changes/`", could classify a quick task that edits OpenSpec change files as managed and then fail it at admission. That is the safe direction (explicit failure), and task 4.1 verifies the predicate against real managed and quick fixtures before implementation.
- The exit-status/classification agreement rule depends on gh behavior; it is gated by task 2.1 fixtures.
- Strict trust-config errors can stop previously "working" runs that had a broken optional config; the failure message names the source so repair is direct.

Reported, not changed: `lifecycle_workers.comments_for`/`list_prs` and `parallel_lifecycle_acceptance` use `--paginate` without `--slurp` through a concatenated-JSON decoder; `agent_friction.current_task_content` and `non_task_names` are best-effort by design for friction binding; `publication_queue._block` swallows `QueueError` when writing the secondary blocked-escalation record (`pass  # status still derives the block from the v1 marker`) and `_integrate` swallows a lost `merged` record after a confirmed merge. These are outside the four observations here and are reported to the Requirement.

## Verification

Behavior-level tests for each sub-outcome run against the shipped scripts: comment history with a fake `gh` returning slurped pages; check observation through the fake-`gh` harness in `tests/test_publication_state.py` with the recorded real gh 2.97 output shapes and queue-level `_integrate` tests; trust configuration with real temp `.dev-platform.toml`/operator TOML files; managed provenance with a temp git repository holding a managed task state and a quick-task branch. Existing tests that assume the downgrade (`test_admission_identity_is_the_task_content_digest_when_proven`) are replaced by explicit managed-failure and genuine-quick-task cases. Source and rendered-template parity follow the standard entrypoints (`python3 scripts/run_test_groups.py --all`, template contract tests). Semantic OpenSpec verification records the actual commands and the limitations above in verification.md before archive or developer handoff. Real dogfood of the full lifecycle remains the separate release prerequisite (#391).
