Durable candidate states. `candidate_lifecycle.py` is pure: it validates v2 markers (`dev-platform-publication-queue:v2`), builds handoff records and derives the state from the latest valid v2 record for the exact PR head (comment-id order), labels and an exact-head required-check snapshot. A record for an older head contributes no gates; a review/repair/finalization claim recorded on an earlier head stays visible with its job and attempts (it still owns the candidate across a coordinator branch update), while any other older-head record contributes no claim or next job; a malformed v2 or v1 marker yields `blocked-escalation` with its reason; v1 admissions read as `ready`, or `integrating` under `publication:active`, with no invented gates; merged/closed PRs and failed or pending exact-head checks override as specified (pending checks keep an `integrating` candidate and its claim; failed checks mark the `required-checks` gate failed and name it as the red gate; a merged candidate has no remaining job). There is no second journal: state is recomputed from GitHub on every read (restart test derives the same state from the same snapshot).

Handoff records. `publication_queue._transition` publishes a v2 record and projects exactly one `lifecycle:<state>` label on every coordinator transition that exists today: admission (`ready`, bound to the managed task-content digest when the admitting checkout is at the admitted head, otherwise exact-head identity; admission itself proves no validation, so its only satisfied gate is `archived-verification`, bound to the task's archived `automated-checks.json` (successful outcome, the task content and head it ran on, and the evidence file's sha256); without that evidence no gate is claimed), worker activation (`integrating`, naming the integration job and its `publication-queue workflow` claim for the exact head), block (`blocked-escalation`, failing gate `publication` with the bounded reason as evidence; the block dequeues the candidate before its best-effort v2 record, never inherits a task identity for a possibly unproven head, and a v1 block written after the latest v2 record still derives as blocked if that record was lost) and merge (`merged`, with the passed `required-checks` gate bound to the merged head; a failure to publish that record after a confirmed merge never turns the merge into a block). Before writing it re-observes the PR head and the latest persisted record for that head (de-duplication never mistakes the derived overlay of a later v1 block for a published record): a moved head publishes nothing, an unchanged state with no new gate, red gate or job/claim is not re-published (so scheduled worker retries cannot exhaust the bounded comment page), gate bindings, items not re-verified and the next job carry forward from the latest exact-head record, and task identity, attempt counters and items not re-verified also carry forward across a coordinator head update (gates bound to the old head do not), while a re-admission binds the freshly validated task-content identity instead of the inherited one. A transition into `integrating`, the merge step after the check wait and the failed/unregistered-check block paths and the generic error path re-check ownership (when ownership cannot be observed, the error path waits instead of blocking): an exact-head record owned by other work, a review/repair/finalization claim recorded on the head observed before a coordinator branch update, or a malformed trusted record stops integration, while an escalation or integration-repair record for an older head never vetoes a freshly admitted head; if review, repair, finalization, escalation or integration repair took the current head in the meantime it publishes nothing and the worker waits. An admission retry recovers a missing `ready` record but refuses to write when any record for that head appeared meanwhile, so it never rewinds or overrides lifecycle work. v1 admission/update markers remain the authority for the existing queue algorithm. Entering `integrating` counts an `integration` attempt (re-entering the same state on a scheduled retry does not), and an unchanged retry still repairs an interrupted label projection. Only comments from repository writers or the configured coordinator App count as lifecycle markers (OWNER always; MEMBER/COLLABORATOR only after the repository permission API proves admin/maintain/write; a failed permission lookup fails the observation closed instead of silently ignoring a possible claim): the queue workflow exports the slug of the App token it minted (`DEV_PLATFORM_COORDINATOR_APP`), a local reader takes it from `[publication] coordinator_app` in the external operator config (configured on this operator machine) or project config, and any other App's or non-writer's comments are ignored rather than trusted or blocking — by lifecycle derivation and by the v1 queue consumers alike.
