## Context

The design assumes `main` with the re-admission change (PR #457, v1.9.4) merged.

- **Candidate contour (finalization).** `post_review_finalization.execute_finalize` refreshes the identity (`pr_review_gate.refresh_identity`) and returns `changed` unless `task_content_identity.equivalent_proofs(recorded, actual)` holds. It then calls `reestablish_gates`, which reruns selected checks only when the `selected-checks` gate is not `reusable` for the identity (after a review repair it never is) and raises `SemanticVerificationRequired` when the semantic gate is not bound. After that it archives, checks the result with `validate_finalization_paths` (fast-forward from the claimed head, archive paths only) and pushes. `trusted_checks_runner` runs `select_checks.py --base origin/main --execute`, plus `--contribution-base` for a contribution. For a non-contribution candidate the gate in `select_checks.main` is therefore `_platform_common.require_fresh_task_base`, which requires HEAD to contain freshly observed `origin/<main>`. Finalization never merges `main`, so any `main` advance after review sends the candidate to `blocked-escalation` (`run_claimed_finalize.blocked`). `tests/test_post_review_finalization.py::test_main_task_finalize_keeps_main_freshness` locks in this defect. The offline `parallel_lifecycle_acceptance.py` uses a scripted `checks_runner`, which is why it never exercised the real gate.
- **Task-content identity.** `content_identity` records `base` = `merge-base(HEAD, origin/main)` at proof time. In a fresh finalize checkout at the claimed head, the same merge-base is that recorded base, or a descendant of it when a coordinator update already merged `main`, and `equivalent_proofs` accepts the move only when main's changes do not touch task paths. That base is the **proven base** of the reviewed content.
- **Integration contour (exists, unchanged).** `publication_queue._integrate` requires finalization (`_require_finalized`) and then calls `_prepare`:
  - it recovers a lost update marker only for a clean `proven + main` merge, or for the `post_review_finalization.derived_merge_only` shape;
  - when main overlaps only the candidate's archive-derived specs it calls `prepare_derived_specs` (a failure is `IntegrationRepairNeeded`);
  - it judges any other overlap by `merge_conflicts` and turns a real conflict into `IntegrationRepairNeeded`;
  - otherwise it merges current `main` cleanly through GitHub `update-branch` and records an `update` marker.

  Required CI then runs on the actual merged head (`required_check_state_for_ref`, `_checks_proven_on` bound to the main it ran against). A failing check is `IntegrationRepairNeeded` and leads to `_integration_repair`, which is bounded by `MAX_INTEGRATION_REPAIRS`. `integration_contour.advance_after_repair` reuses evidence (never `required-checks`) for unchanged content and calls `return_to_review` for changed content.
- **Review reuse (exists).** `pr_review_gate.run_claimed` finishes a review job without launching a reviewer when the candidate's `review` gate is `reusable` for the job identity (`reused-review`). Coordinator updates carry content-bound gates (`publication_queue._transition`), and so do finalization and unchanged-content integration repair. Re-admission does not. `publication_queue.admit` writes the supersession's `review-pending` record with `inherit_identity=False` and only the handoff gates (`developer-friction`, `selected-checks`, `semantic-verification`), so the passed review is dropped and a full LLM review follows.

## Decisions

1. **Bounded freshness contract in `select_checks.py`.** A new `--proven-base SHA` option, validated in `main()` through a new `_platform_common.require_proven_task_base(root, sha, remote, main_branch)` before any command starts:
   - Preconditions: `--execute` present; `lifecycle_mode(config) == "coordinator"`; not combined with `--evidence`, `--contribution-base`, or protected-full mode (`--mode protected-full`, `--protected-full`, `--full`).
   - Base check: `SHA` is a full 40-hex commit id, and `git merge-base HEAD origin/<main>` equals `SHA`. This proves that HEAD contains `SHA`, that `SHA` lies on main's history, and that HEAD lacks only commits main gained after the proven base.
   - The main-merge-base form applies to every candidate. A legacy dependent child's checkout-local requirement context (gitignored, absent from the disposable finalize clone) does not change the contract: if such a context steers the review identity base away from the main merge base, `--proven-base` refuses explicitly and finalization escalates; the contract never trusts checkout-local context.
   - Any violation exits non-zero, names the condition, and nothing is substituted.
   - When `requires_task_freshness(checks)` holds, this check replaces `require_fresh_task_base`, and the success line names the coordinator-finalization contract and the base. The option is validated even when no full set is selected.

   Without the option the gate is byte-for-byte unchanged, so developer preflight still requires fresh `main` and protected CI is untouched. A developer cannot turn this mode into handoff evidence: handoff (`pr_review_gate.handoff_gates`) requires the `--evidence`-written `automated-checks.json` with `gate_task_content`, and the option refuses `--evidence`.
2. **Finalization runs real checks on the proven base.** `post_review_finalization.trusted_checks_runner(checkout, env, *, contribution_base=None, proven_base=None)` requires exactly one keyword and fails loudly with neither or both. It passes `--proven-base` or `--contribution-base` and returns a description `{"command": [...], "freshness": {"contract": "proven-base"|"contribution-base", "base": sha}}`. `execute_finalize` takes the proven base from `actual["task_content"]["base"]`. That identity was already proven equivalent to the job's recorded identity, which binds the base to what was reviewed. A missing or malformed base raises `WorkerError("candidate identity lacks its proven task-content base")`. The runner becomes `functools.partial(trusted_checks_runner, proven_base=base)`, and contributions keep `contribution_base`. The harness runs those checks in a credential-free environment with a scratch home; it pins the operator's Python user base (`PYTHONUSERBASE`), because the scratch home otherwise hides user-installed check tooling such as `copier` (observed in the readiness dogfood: render tests failed with `No module named 'copier'`); the user base holds no credentials. Three central-checkout tests (`test_template_contract`, `test_central_dogfood_lifecycle`, `test_deepseek_harness_runtime`) treated any `.dev-platform.toml` as the central operator config; in a disposable checkout it is the installed public `dev-platform/source-contract.toml`, so they now skip there exactly as they already skip when the file is absent. `reestablish_gates` records the runner's description in the harness-executed `selected-checks` evidence in place of the hard-coded `origin/main` command string. A runner that returns no description is an error. Failing commands still raise `WorkerError`, so finalization escalates as before. The semantic-verification gate is unchanged: after a repair it still requires the developer's content-bound receipt.
3. **Finalization never merges `main`.** No code path in `execute_finalize` fetches or merges `main`. The invariant is pinned by regression tests: with `main` advanced, the pushed finalize commit has the claimed head as its only parent, and `validate_finalization_paths` still refuses anything beyond the archive move.
4. **The integration contour keeps base actualization.** `_prepare`, `derived_merge_only`, `prepare_derived_specs`, `merge_conflicts`, `_integration_repair` and `advance_after_repair` are unchanged. Validating the task content on its proven base does not replace required CI on the actual merged candidate, which stays mandatory before the guarded merge.
5. **Review reuse on re-admission.** In `publication_queue.admit`, the supersession branch reads the superseded lineage record (refactor `_supersession` to return it with the `supersedes` payload). It then carries every lineage gate that is `pr_review_gate.reusable(root, gate, identity)` for the new handoff identity, rebound to that identity (as `advance_after_repair` does). Two kinds of gate are excluded: `required-checks`, which is bound to an integration head and main, and the names the handoff supplies, so fresh developer evidence wins. The result goes into the `review-pending` transition as `gates={**carried, **handoff_gates}`. The published review job then completes through the existing `reused-review` branch of `run_claimed` without launching a reviewer. Only a `passed` gate is reusable, and the `_supersession` guards are unchanged: an unchanged digest is still refused over finding-level escalations or material findings. Changed content, including a substantive conflict fix and a main merge that overlaps task paths, is not equivalent, so it gets a fresh review. A clean merge of `main`, a `main` advance and lifecycle archiving keep the review.

## In-place recovery of lehard/dev-platform#455

#455 is `blocked-escalation` at `d11a5ca` with red gate `finalize` (the freshness failure). Its record carries a passed `review` gate for digest `19766e…` with base `f180505`. Selected-checks and semantic-verification are absent because the codex repair changed the content. The operator path after this change is released and the coordinator workers run the released trusted scripts:

1. `python3 scripts/publication_queue.py resume --pr 455 --reason "finalize proven-base contract released (BR-536)"`. The v1.9.4 finalize resume re-offers finalize at `d11a5ca` with identity and gates kept.
2. `python3 scripts/lifecycle_workers.py work-next --repo lehard/dev-platform --kinds finalize --run`. Finalize proves the identity unchanged and runs the real selected checks with `--proven-base f180505…`; a real failure escalates again. The candidate then becomes `blocked-retryable` / `semantic-verification`, because the repaired content has no bound receipt. This is the existing developer gate, not a freshness block.
3. The task developer brings the task worktree to `d11a5ca`, performs semantic verification of the repaired content, and refreshes `verification.md`. Then `dogfood_task.py reconcile` (developer preflight still requires fresh `main`), selected checks with `--evidence`, a commit, the friction checkpoint and `finish`. This re-admits the descendant head in the same PR with `supersedes`. The passed review is carried because the content is equivalent across the clean main merge, so the review job reuses it without an LLM run. Finalize archives with all gates reusable, the candidate becomes `ready`, and the queue merges current `main`, runs required CI and merges.

No check is bypassed, no PR is closed, and the candidate is not rerun through the whole lifecycle.

## Risks

- Checks on the proven base cannot see an incompatibility with newer `main`. That is the integration contour's job: required CI on the merged head fails, and the failure goes to bounded integration repair. This is the intended division, but such a failure is found later than before.
- `--proven-base` lives in a downstream-rendered script. It refuses outside coordinator mode, so downstream behavior is unchanged. A local operator in the source repository could still run it by hand, but the run produces no handoff evidence and no gate.
- After a review repair, finalization runs checks and then stops at the semantic-verification developer gate. The checks run is not recorded in that case; the developer re-handoff supplies its own evidence.
- The change depends on #457 (`resume` for finalize, supersession) being in `main` first.
- Out of scope, recorded follow-up: a Requirement contribution's semantic re-handoff (`blocked-retryable` / `semantic-verification` → block → fresh admission in `publication_queue.admit`) does not pass through supersession and still drops a passed review; carrying gates there is a separate change.

## Routing

Recommended start tier `R2`. The architecture is fixed by the owner, the diagnosis is reproduced on #455, and the changes are bounded to three existing modules with deterministic tests and a real dogfood gate. No `R3` hard trigger applies.

## Verification

Unit and fixture tests, using real git repositories where the base relation matters:

- (a) Two independent candidates are reviewed without repair. A merges and advances `main`. B finalizes (gates reused, no checks, no `main` merge), integrates on the new `main` with required checks on the merged head, and merges with no developer action.
- (b) After a real review repair, `main` advances before finalize. Finalize runs the real `select_checks` with `--proven-base` equal to the identity base, the freshness gate passes without HEAD containing current `main`, and the candidate is not escalated for freshness. It reaches the semantic-verification gate, or `ready` once that gate is bound.
- (c) The developer merges the new `main` cleanly and re-admits with unchanged task content. The passed review is carried, and the review job completes as `reused-review` without launching a reviewer.
- (d) An integration repair or re-admission that changes task content (a substantive conflict fix) drops the review and runs a new one. A main merge overlapping task paths is not treated as unchanged.
- (e) A failing selected check under `--proven-base` escalates finalize. A real merge conflict or a failing required check becomes integration repair. `--proven-base` refuses `--evidence`, `--contribution-base`, protected-full, portable mode, a non-merge-base SHA and a missing `--execute`. Without the option, a stale developer head is still blocked by the freshness gate. The integration contour still requires required CI on the merged head.
- `test_main_task_finalize_keeps_main_freshness` is replaced by a proven-base assertion. The contribution-base tests stay.
- Readiness, before release: a real dogfood of the parallel lifecycle (BR-391 and its acceptance task), with `main` moved by another merge between review and finalize of a repaired candidate. Its evidence is recorded in `verification.md`; unit tests alone are not sufficient. The finalize harness runs the worker checkout's own trusted scripts (`trusted_checks_runner` resolves `select_checks.py` next to itself), so a finalize worker launched from this change's checkout exercises the change before merge. When the coordinator uses the released scripts, the #455 recovery above is performed and reported on the Requirement.
