## Semantic review

**Completeness: PASS.** Every delta-spec requirement is implemented and covered by a test:

- *Managed routing recommends an abstract start tier during authoring* -- `managed_task.py create_task()` calls `start_tier_routing.recommend_start_tier()`, prefixes the Issue title (`title_prefix`), and embeds the receipt in the published package/provenance; no concrete model ID is recorded. Covered by `test_create_task_prefixes_title_and_embeds_r2_receipt_by_default` / `test_create_task_r3_requires_a_supported_trigger_and_prefixes_title`.
- *Frontier routing is trigger-based rather than risk-size based* -- `recommend_start_tier` has no diff-size/file-count/blast-radius parameter at all; `R3` is reachable only through one of six enumerated `STRONG_TRIGGERS`. Covered by `test_diff_size_style_reasoning_is_not_a_supported_trigger`, `test_high_assurance_is_independent_of_tier`.
- *Execution tier, reasoning effort and assurance are independent routing dimensions* -- the routing receipt carries `assurance`/`effort_hint` orthogonally to `recommended_start_tier`; nothing derives tier from assurance. Covered by `test_high_assurance_is_independent_of_tier`.
- *Execution confirms freshness and escalates only on new evidence* -- `model_routing.prepare(..., profile=None)` derives the profile from the authored tier (`tier_to_profile`) and records `freshness="confirmed"`; `escalate()` now records `freshness="escalated"` and still only rewrites the routing JSON (canonical OpenSpec/worktree/diff untouched). Covered by `test_prepare_without_profile_confirms_authored_r2_tier`, `test_prepare_without_profile_confirms_authored_r3_tier`, `test_escalate_marks_route_as_freshness_escalated`.
- *Provider-local delegation remains a secondary execution capability* -- no code path requires a strong-parent session before `route-codex`/`route-claude` can run; `dogfood_task.py`'s `--profile` is now optional at the CLI layer too. Covered by `test_route_codex_omits_profile_when_confirming_authored_tier`, `test_route_claude_omits_profile_when_confirming_authored_tier`.
- *Routing v2 reuses truthful execution provenance* -- see the explicit judgment call below.

**Correctness: PASS**, with one explicit judgment call recorded rather than silently resolved. `development-backlog#5` (the dependency this change was told to wait for and reconcile) is **not archived** at implementation time -- its own task 6.11 (Codex leg) is blocked on provider credits until 2026-08-18, and its section 7 (verify/archive/release) has not started. The user explicitly authorized starting `#29` regardless. Rather than depending on #5's not-yet-landed `Route.supervisor`/`execution.participant` provenance schema (which only exists in #5's separate, unmerged worktree), this change satisfies "do not create a parallel telemetry/state machine" by extending the *same* `.claude/model-routing/<change>.json` `Route` record that already existed (additive `start_tier`/`freshness` fields, `_read_route` defaults them for old records via `payload.get(...)`) instead of adding a second file/schema. When #5 eventually lands its own additive fields on the same record, reconciling is a field-level merge, not a rewrite. `tasks.md`'s first item is left `[~]` (not `[x]`) to keep this honest instead of claiming a dependency was satisfied when it was not.

A second, smaller judgment call: `model_routing.escalate(reason)` still accepts free-text rather than being constrained to the six `STRONG_TRIGGERS` categories. The delta spec's "Under-routing triggers controlled escalation" requirement (carried over unchanged from the current accepted spec) already allows escalation for reasons beyond a frontier trigger -- material OpenSpec conflict, unexpected scope, low confidence, repeated verification failure -- so constraining execution-time escalation to the authoring-time trigger enum would have silently narrowed existing, still-valid escalation grounds. The six-category enum is enforced where the spec actually requires it: authoring (`recommend_start_tier`) and package import (`validate_routing_receipt`, defense-in-depth against a hand-edited `R3` claim).

**Coherence: PASS.** `proposal.md`/`design.md`/`specs/model-routing/spec.md` (the delta materialized from the Development Backlog Issue, formally repaired twice, both purely structural and not semantic):

1. Before import, a missing `#### Scenario:` block on "Provider-local delegation remains a secondary execution capability" was added to the source GitHub Issue comment so the package could pass `openspec validate`'s scenario requirement.
2. Before archive, the delta's category headers were restructured: the entire delta had originally been authored under a single `## MODIFIED Requirements` header, but `openspec archive` matches `MODIFIED` by exact existing requirement title, and none of the six new titles matched any of the six titles in the currently accepted `openspec/specs/model-routing/spec.md`. Reorganized into `## REMOVED Requirements` (the old "Model routing occurs at execution preflight, not backlog authoring", whose core claim this change inverts), `## ADDED Requirements` (four genuinely new requirements: the authoring-time recommendation, the trigger-based-not-risk-size-based rule, tier/effort/assurance independence, and provenance reuse), and `## MODIFIED Requirements` against the two existing titles this change actually extends in place ("The platform exposes abstract execution profiles" absorbed the "strong parent not mandatory"/entrypoint content, and "Under-routing triggers controlled escalation" absorbed the freshness-check framing). The previously-separate "Provider-local delegation remains a secondary execution capability" requirement was folded into "The platform exposes abstract execution profiles" during this merge since both scenario sets described the same entrypoint behavior against the same profile requirement; every `SHALL`/`MAY` normative statement and every scenario from the original six requirements was preserved verbatim or folded without loss (two near-duplicate "starts directly" scenarios that had been authored separately in two different requirements were combined into one non-redundant scenario once they landed under the same requirement).

With that structural reconciliation, `tasks.md`, the implementation, and `docs/engineering/model-routing.md`/`AGENTS.md`/`template/AGENTS.md.jinja` all agree on the same shape: `R2` default, `R3` trigger-gated, tier/effort/assurance independent, freshness-confirm-or-escalate at execution time, strong parent no longer a mandatory entrypoint, and no new provenance state machine.
