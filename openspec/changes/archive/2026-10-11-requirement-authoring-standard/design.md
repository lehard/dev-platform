## Context

- A Business Requirement is a Development Backlog Issue with `## Outcome`, optional `## Context`, `## Acceptance evidence`, `## Exclusions`, required `## Target repository` and the `requirement-children` block. `requirement_intake.py create` (and the connected-GitHub transport) validates routing, labels, structure and Project membership; it does not and must not judge meaning.
- Capabilities are project-owned opt-in (`dev-platform/capabilities.toml` `enabled = []`), but every released descriptor and its Markdown is delivered by Copier under `dev-platform/capabilities/` (as `add-intents.md` is already linked from task-intake). `AGENTS.md` and `docs/engineering/*` are always delivered and always read at the matching concern.
- A ChatGPT Project has no checkout and cannot load an Agent Skill; it reads repository files through connected GitHub and follows `chatgpt-project-protocol.md`.

## Decisions

1. **One source: the capability Markdown.** `dev-platform/capabilities/requirement-authoring.md` holds the standard and its examples. Docs and the protocol link to it and state only the trigger and the boundary, never restate the rules, so no surface forks the content. The template carries the same file (the existing mirror convention), so downstream projects and a ChatGPT Project reading the target repository see the identical text.
2. **No enablement required to be effective.** The concern row in `AGENTS.md` ("authoring or materially refining a Business Requirement body") and the task-intake/protocol sections make reading the file part of the normal fixation path for every surface. Enabling the capability only adds the native provider skill for auto-discovery; it is not a prerequisite and adds no per-project step.
3. **Where it sits in the flow.** Fixation (`зафиксируй`) and material refinement of an existing Requirement apply the standard before `requirement_intake.py create` or the connected equivalent writes the body. It does not add a stage after `create`, does not alter `start`, pre-authoring or ADD, and quick tasks are untouched. A trivial request produces a compact body without empty sections or questions.
4. **Three obligation levels in prose, not syntax.** The standard names *fixed*, *meaning fixed / execution variable* and *delegated* and tells the author to make the level evident from wording (for example "verbatim", "must convey", "executor's choice within X"). No new Issue format, labels or fields are introduced, so the Requirement format and routing stay identical.
5. **Supersession and chronicle.** Only an explicitly accepted later decision replaces an earlier one; a last-mentioned option, an agent suggestion, a quote or a hypothesis is not acceptance. Incompatible material versions with no determinable accepted one produce a question. A refinement rewrites the whole current Requirement (Outcome, scenarios, Exclusions and Acceptance evidence) as one contract; it never appends "new decision" over old text and never hand-edits the children block or lifecycle-owned markers.
6. **Selective questions reuse existing machinery.** Questions are asked before fixation only for unresolved material product choices (outcome, rights, money/data invariants, material scope, meaning of earlier decisions), 1–3 grouped with options and consequences; minor gaps are delegated. A critical unresolved choice is never written as agreed; the author asks first, or keeps the idea under the existing Incubator contract. This defers to `goal-definition` and `selective-domain-interrogation` for their cases and leaves system-design questions to ADD.
7. **References.** The author preserves any material the executing agent can reach (link to a stable permitted location, attached asset in the permitted private channel) and states which properties are mandatory. An attachment the executor cannot reach is named as unavailable; a mutable site root is never substituted. No private conversation text, secrets or full external documents are copied into the Requirement.
8. **Self-check is author discipline.** Six questions (coverage, consistency, scope, autonomy, portability, truthfulness) run before writing and after material edits. They are instructions, not a validator: no scorecard, no LLM judge, no recorded status, no approval step.
9. **Verification without overclaiming.** A deterministic eval fixture carries representative cases (long discussion, stale options, reference, verbatim text vs example, autonomy boundary, local prohibition, trivial request, unresolved material fork, already answered question) with objective verifiers over the standard's text and the example records. Tests render the Claude and Codex provider skills and assert identical standard content and that the connected-GitHub protocol links the same file. Live multi-provider behavioral runs are not available deterministically and are not claimed; a bounded readiness check applies the standard to a real or representative conversation in a managed project after release and is recorded in the Requirement retrospective.

## Risks

- Authors may skim the file. Mitigation: the standard is compact, example-led and proportional; AGENTS.md pointer and the capability skill make it reachable in the moment of fixation.
- The rule set could harden into ceremony. Mitigation: explicit non-requirements (no interview, no validator, no empty sections) are tested.
- The mirror between `dev-platform/` and `template/` can drift; the existing parity checks and an added content-hash assertion cover it.
