## Context

Verified against `main` at bd7f234.

Workflow (`.github/workflows/publication-queue.yml`): job `publish-next` mints an App token with `actions/create-github-app-token` from `vars.DEV_PLATFORM_APP_CLIENT_ID` and `secrets.DEV_PLATFORM_APP_PRIVATE_KEY` (scoped to the current repository, `permission-contents: write`, `permission-pull-requests: write`), then runs `python3 scripts/publication_queue.py worker` with `GH_TOKEN` and `DEV_PLATFORM_COORDINATOR_APP: ${{ steps.app-token.outputs.app-slug }}`. Nothing validates these inputs before candidate work. `.github/workflows/rollout.yml` validates its own App inputs inline in shell, so no shared preflight exists for the coordinator; `scripts/cloud_maintenance_preflight.py` and `scripts/private_platform_health_preflight.py` are workflow-specific probes that report available/degraded and are not reusable here. `template/scripts/platform_doctor.py` and `agent_doctor.py` are unrelated health reports.

`publication_queue.py`: `trusted_apps(root)` unions `DEV_PLATFORM_COORDINATOR_APP` with `[publication] coordinator_app` from project and operator config. On a contradiction between sources both names become trusted, and an empty env value is simply dropped. (Its `except Exception: continue` on config read is the defect owned by the `publication-observation` child, which makes the reader fail closed; this child consumes that reader.) `main()` installs `use_default_friction_sink(root)` for `worker`, and `lifecycle_workers.main` installs it for `work-next`. `worker()` starts with `_repo(root)` and `_queued(...)` and has no configuration gate.

Friction: `emit_friction` is called from `_transition` and `publish_job`; it builds an event with `dedupe_key = coordinator:<sha256(number, kind, head, attempts)[:24]>` and calls the sink. `integration_contour.default_friction_sink` resolves the Requirement lineage and calls `agent_friction.append_coordinator_event`, which appends to `log_path()` (`.claude/agent-friction.jsonl`) with a random uuid event id and the docstring "local only". On an ephemeral runner this file is discarded with the job. `requirement_retrospective._check_events`, `agent_friction.events_for_task`, `current_lifecycle_failures`, `current_retrospective_signals`, `mandatory_signals` and `evidence_source_status` all read only that local log, and `evidence_source_status` reports `friction-log: available` regardless. Verified defect: coordinator friction produced in CI is unreachable by the Requirement retrospective.

The existing durable channel is the PR lifecycle comment history: immutable versioned marker comments (`v1` admission, `v2` handoff, claims, results) authored by the coordinator App and authenticated by `candidate_lifecycle.trusted_marker_comment` against `trusted_apps` and proven `trusted_writers`. Routing friction to GitHub process issues (`agent_friction.route_event`) was considered and rejected as the evidence channel: it is sanitized and deduplicated by cause fingerprint across tasks, carries no exact head/stage/worker binding, targets the platform repository rather than the candidate, and records failure as `pending` in the local state file (a silent local-only outcome).

## Goals

- One preflight entrypoint for CI and local runs that proves required configuration before any candidate observation, fails loudly with the input name, and never emits credential values.
- Coordinator friction persisted through the existing authenticated PR comment channel, bound to Requirement, head, stage and worker, readable by the Requirement retrospective on any machine.
- Persistence or readback failure is visible; no silent local-only outcome in CI.

## Decisions

1. **Preflight is a `publication_queue.py` subcommand with explicit mode and phase.** `preflight --mode ci|local --phase inputs|runtime|all`, both flags required (no autodetection of CI, no default phase). Output is JSON `{"state": "ok"|"error", "mode", "phase", "checks": [{"name", "status": "ok"|"failed", "detail"}]}`; the process exits 0 only on ok and 2 on any failure, matching the existing `QueueError` exit. It stops at the first failed check and names it. `detail` strings are built only from input names (env var, config key, endpoint template) and fixed categories; token, key and response bodies are never formatted into output, and `gh` stderr is discarded rather than echoed (same discipline as `cloud_maintenance_preflight._api`). The App slug is a public identity, not a credential, and may appear in a contradiction message.

2. **Checks.**
   - `inputs` phase, mode `ci`: `PREFLIGHT_APP_CLIENT_ID_SET` and `PREFLIGHT_APP_PRIVATE_KEY_SET` equal `true`; `GITHUB_REPOSITORY`, `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT` are present and well formed; `gh`, `git` and Python 3.11 (`tomllib`) are available. The workflow sets the two flags from `${{ vars.X != '' }}` / `${{ secrets.Y != '' }}` expressions, so the private key never enters the preflight process and the step runs before the token is minted, turning the generic `create-github-app-token` failure into a named one. Mode `local`: `gh` and `git` available and `gh auth status` succeeds (exit code only, output discarded).
   - `runtime` phase: `GH_TOKEN` is non-empty (mode `ci`); the coordinator App identity resolves: in `ci`, `DEV_PLATFORM_COORDINATOR_APP` is non-empty and matches `^[A-Za-z0-9][A-Za-z0-9-]*$`, and if `[publication] coordinator_app` is configured in project or operator config it must equal it (a difference is reported as `coordinator App identity contradiction: environment names X, configuration names Y`); in `local`, a `coordinator_app` must be configured. Trust configuration is read through the strict `trusted_apps` reader delivered by `publication-observation`; an unreadable or invalid source surfaces as that reader's named error and the resulting set must be non-empty and contain the resolved identity. `enabled(root)` is true and `_repo(root)` equals `GITHUB_REPOSITORY` in `ci`. Token scope and permission proof are read-only probes through `_gh`: `repos/{repo}/pulls?per_page=1` is readable; in `ci`, `installation/repositories` succeeds and lists the repository (proving an installation token for exactly this repository); `repos/{repo}/collaborators/{slug}%5Bbot%5D/permission` reports a permission in the existing `_WRITER_PERMISSIONS`; in `local`, `repos/{repo}` reports `permissions.push` true. Contents-versus-pull-requests granularity cannot be proven without a mutation, so it is guarded statically: a workflow test pins `permission-contents: write`, `permission-pull-requests: write` and no other `permission-*` input (already required by the existing least-privilege requirement).
   - Probes classify failure by fixed category (`unauthorized`, `not-found`, `unreachable`) derived from the exit status and HTTP status line without echoing bodies.

3. **Preflight is wired at three points, all through the same function.** The workflow gains a step `Preflight inputs` before the token step and `Preflight runtime` after it and before `Process next admitted PR`; `worker` becomes `worker --mode ci` in the workflow and calls `preflight(root, mode, "all")` first in-process, so a local `python3 scripts/publication_queue.py worker --mode local` run and any future launcher cannot skip it. `worker` therefore gains a required `--mode`; the existing documented operator invocation in `docs/engineering/agent-workflow.md` is updated. Preflight failure returns the `error` result with exit 2 before `_repo`/`_queued` are reached. `lifecycle_workers work-next` is not given a preflight here (owned by `worker-runtime-identity`); it only needs the sink identity in decision 6.

4. **Durable evidence record = a new marker type in the existing comment channel.** `EVIDENCE_PREFIX = "dev-platform-publication-queue:evidence:v1 "` followed by JSON: `version`, `kind: "coordinator-friction"`, `requirement` (owner/repo#N from lineage, or null only when lineage proves the task has no Requirement), `number` (PR), `head` (full SHA), `stage` (the lifecycle state/kind that triggered it), `worker`, `dedupe_key`, `event_id`, `at`, and the bounded sanitized event fields (`category`, `severity`, `triggers`, `observation`, `evidence`, `hypothesis`, `proposal`, each limited through `agent_friction.normalize_text`). It is a separate comment rather than an extra field on the v2 handoff record so the handoff schema, its validation and the carry-forward rules in `candidate_lifecycle` stay untouched, and so a retried transition cannot rewrite handoff state to add evidence.

5. **Authentication and idempotence.** Evidence comments are trusted only when `trusted_marker_comment` accepts the author against the strict trusted App set and proven writers, exactly like other markers; an untrusted author's forged record is ignored. Before posting, the sink reads the complete history (the paginated reader from `publication-observation`) and skips the POST when a trusted evidence record with the same `dedupe_key` exists. A trusted record with invalid JSON, wrong version, a PR number or head that contradicts its comment's PR, or missing binding fields raises a named `QueueError` on read (the same rule as the v1/v2 markers), never silently skipped.

6. **Worker identity binding.** `worker()` resolves one run identity at start and passes it to the sink: `ci` -> `github-actions:<GITHUB_REPOSITORY>:<GITHUB_RUN_ID>:<GITHUB_RUN_ATTEMPT>` (all three required by preflight); `local` -> `local:<hostname>:<pid>:<uuid4 generated once at start>`. These are constructed per run, not defaulted from a possibly missing value. `use_default_friction_sink(root, *, worker)` requires the identity, `emit_friction` adds it to the event, and a sink installed without one raises. `lifecycle_workers.work-next` passes its `--worker` value. When `worker-runtime-identity` lands its validated identity resolver, `worker()` adopts it with a one-line change; the evidence field keeps the same name.

7. **Sink behavior.** `integration_contour.default_friction_sink` becomes: resolve lineage (a failure propagates, today's behavior), post the durable record (decision 5), then mirror to the local log via `append_coordinator_event` using the same `dedupe_key` and a deterministic id `coordinator-<first 16 hex of the dedupe digest>` (new optional `event_id` argument; existing events keep their uuid). Durable first, local second: a durable failure raises before anything is claimed. `emit_friction` already converts sink failures into `QueueError("friction recording failed ...; retry transition")` raised before `_transition` posts the handoff record, so the transition is not published and `worker` exits 2: the failure is visible and retryable. There is no mode in which CI records only locally.

8. **Retrospective readability.** `publication_queue.requirement_evidence(root, requirement, children)` lists candidate PRs via a helper extracted from `requirement_status` (same inventory rules), reads each complete history and returns trusted evidence records as event dicts (`id` = `event_id`, `task` = candidate branch, `requirement`, `attribution: "coordinator"`, `durable: {number, head, stage, worker}`). `agent_friction.events_for_task(task, children)` merges those for Requirement refs (`owner/repo#N`) with local events by id; local-only developer tasks are unaffected and never call GitHub. `_check_events` validates ids against the merged set. `requirement_retrospective review-path` includes `durable` provenance in `recorded_signals`; `mandatory_signals`, lifecycle-failure and retrospective-signal rules apply to durable events exactly as to local ones, so a durable `high` lifecycle failure or workaround trigger must be linked or classified. `evidence_source_status(requirement=None)` adds `coordinator-evidence` for a Requirement: `available`, or `unreadable` when `gh`/GitHub or a trusted record's shape fails, so `unaccepted_gaps` names the gap and the checkpoint refuses it unless explicitly accepted with `--accept-gap coordinator-evidence`. Reading failure is never converted into an empty event list.

9. **Local friction capture, process-issue routing and the friction state file are unchanged.** Coordinator events still are not routed to GitHub process issues from the sink; a human-visible finding is promoted through the existing path after the retrospective links it.

## Risks

- The write-permission probe for an App bot via `collaborators/{slug}[bot]/permission` is the closest read-only proof available; its behavior with installation tokens must be confirmed in real dogfood (#391). If GitHub does not report a permission for an installation token, the task records that as a blocker and a different proof is proposed; no skipped check or assumed pass is introduced.
- Evidence comments grow the PR comment history. Dedupe keys include head and attempt counters and the paginated reader removes the old size ceiling; bodies are bounded by `normalize_text`. A pathological flapping state is bounded by the existing attempt counters.
- The preflight adds `gh` API calls on every five-minute scheduled run; they are three small reads and run before candidate work only.
- `worker` gains a required `--mode`, a breaking change for hand-run invocations; the only in-repo caller (the workflow) and the documentation are updated, and omission is a usage error rather than a guess.
- Scheduling of this child behind `publication-observation` is required because both preflight and evidence reading use its strict trust reader and complete comment reader; neither is re-implemented here.
- Existing fallbacks reached in touched code and left unchanged, reported rather than extended: `agent_friction.read_events` returns `[]` on an unreadable log and skips malformed lines (surfaced as a gap by `evidence_source_status`); `agent_friction._unknown_run_provenance` fills unknown run provenance for coordinator events; `lifecycle_workers.main --worker` defaults to `worker-<pid>` (owned by `worker-runtime-identity`).

## Verification

Unit tests with a fake `gh` and patched environment cover each preflight check and its failure, including a canary secret value in `GH_TOKEN` and the flag env that must not appear in stdout/stderr/JSON. A workflow-structure test asserts step order (inputs preflight before token step, runtime preflight after it and before the worker) and that no secret is passed to the preflight step. Evidence tests cover record round-trip, idempotent retry, forged author, malformed record, persistence failure leaving no handoff record, deterministic id shared by durable and local mirror, and the retrospective review-path/checkpoint/gap behavior including a clean checkout with an empty local log. The standard source and template checks run; real lifecycle dogfood remains a parent release prerequisite.
