# Proposal: Requirement-level retrospective

## Why

The technical child checkpoint cannot observe problems before child materialization or between several children. A clean set of children can therefore close a Requirement without classifying significant process friction from the whole path.

## What changes

Introduce a bounded parent retrospective at the terminal Requirement boundary. The result is a concise clean checkpoint or links to existing friction events; meaningful findings use the current process-issue router. Terminal reconciliation checks fresh parent evidence before Done. The child retrospective remains separately required.

## Success evidence

Representative tests cover a pre-child finding, a cross-child finding, clean completion, stale or missing checkpoint rejection, and preservation of child checks. Documentation explains how specialized stages contribute to the same learning loop.

## Constraints

Use existing friction/process-issue authority. Do not add a second backlog, status ledger, or long report. The parent checkpoint must be resumable without inventing success evidence.
