## Context

- `_platform_common.require_fresh_task_base` fails unless HEAD is `equal`/`ahead` of freshly fetched `origin/main`. `select_checks.py` calls it before evidence-producing execution unless `--proven-base` (coordinator finalization) or `--contribution-base` (Requirement contribution) is given.
- `finish_task.py` adds a `task-freshness` blocker when `task_reconciliation.observe` reports `behind`/`diverged`, and a `branch-base` blocker for a first publication whose branch does not contain `origin/main`.
- A coordinator candidate never reaches those `finish_task.py` blockers: `finish` routes it to `finish_developer_handoff` first, whose first-publication fresh-base check is `project_publish.push_feature_branch(require_fresh_base=True)`. `publication_queue.admit` has no freshness check; it records current main as the admission base.
- `independent_review.request_staleness` already accepts a clean irrelevant main merge through task-content proofs.
- `publication_queue._prepare` merges current main into the admitted head through GitHub `update-branch` when the head does not contain main; `_integrate` merges only when required checks on that integrated head pass; a merge conflict blocks the candidate.

## Decisions

1. **One classifier.** Add `observe_task_base_currency(root, remote, main_branch)` next to `observe_task_base_freshness`. It fetches main once (reusing the existing fetch helper), and returns `fresh`, `behind-disjoint` or `reconcile-required` with the observed main sha, the merge base, and, for `reconcile-required`, the overlapping paths (sorted, bounded) or the conflict. Disjointness compares `git diff --name-only <base> origin/main` with `git diff --name-only <base> HEAD` including renames' old and new paths. The clean-merge test is `git merge-tree --write-tree HEAD origin/main` exit status (git >= 2.38). A fetch failure or missing merge base raises `TaskFreshnessError` as today; nothing is assumed.
2. **Where it applies.** A helper `coordinator_candidate(root)` is true only when the repository's publication contract is the coordinator queue: it is `pr_review_gate.managed_candidate`, the predicate `finish` already uses to route a task to the developer handoff and queue admission (coordinator lifecycle mode, the queue workflow on main, an active canonical managed change). It is consulted only for a head that does not contain main, so a fresh head never depends on it; a missing or unsupported contract raises. Only then do `select_checks.py` evidence-producing execution (`--evidence` in `local-affected` mode, without `--proven-base`/`--contribution-base`) and the developer handoff accept `behind-disjoint`. The handoff gate is `project_publish.push_feature_branch(..., coordinator_handoff=True)`, passed only by `publish_pr(developer_handoff=True)`, which has already proven the candidate. The `finish_task.py` `task-freshness`/`branch-base` blockers stay unchanged because a candidate never reaches them, and admission stays unchanged because it has no freshness gate. Every other path, including protected-full and non-evidence execution, keeps `require_fresh_task_base` unchanged.
3. **Recorded, not silent.** On `behind-disjoint` the freshness line prints the contract, the observed main and the merge base, and the evidence payload records `"task_base": {"contract": "behind-disjoint", "main": <sha>, "base": <sha>}`, so a reviewer of the evidence sees that main was not contained. The handoff prints the same contract line before pushing.
4. **Status.** `task_reconciliation.Freshness` gains the `behind-disjoint` state with `reconcile_required == False` for coordinator candidates; `status` prints it with the merge base, and a candidate that must reconcile gets the overlap or conflict as detail. Status stays read-only: when main's commit is absent locally it fetches only main's objects (`git fetch --no-write-fetch-head --refmap= origin refs/heads/<main>`), never a ref. `reconcile` keeps the plain observation, so an explicit reconcile still merges main into any head behind it.
5. **Final gate stays.** The queue's integrated-head required checks remain the merge gate. A semantic break from main that touches no candidate file surfaces there and goes through the existing integration-repair path.

## Risks

- A main change in another file can break the candidate semantically (e.g. a renamed caller). The integrated-head CI catches it before merge, at the cost of an integration-repair round instead of a developer full run. Accepted: that is the existing cloud-final contract.
- `git merge-tree --write-tree` needs git >= 2.38; the local machine has 2.39 and GitHub runners are newer. An older git fails the classifier explicitly.
