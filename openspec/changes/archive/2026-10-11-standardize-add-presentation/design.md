## Context

- `template/scripts/add_intents.py` owns the ADD document (`requirement.summary`, `evidence`, `reused_constraints`, `elements` with `category`/`status`/`statement`, `assumptions`, `contradictions`, `unresolved_choices`, `approved`, `approval`) and its checks: `validate_add`, `add_content_digest` (everything except `approved`/`approval`), `approve_add`. Freshness comes from `prepared_against`, snapshot evidence and bound sources.
- Capability Markdown is delivered by Copier under `dev-platform/capabilities/`, reachable without enabling the capability; `scripts/add_intents.py` is a thin adapter over the template implementation.
- Claude and Codex agents, ChatGPT Project and managed projects must read one text; nothing may fork it.

## Decisions

1. **Boundary is guidance, not a gate.** The capability Markdown gets a section stating the five destinations of a candidate (BR/already accepted, existing technical contract, ADD delta, OpenSpec detail, open product question), the key test ("what is the new material system decision relative to the current accepted state that cannot simply be read from the BR and the existing contract?"), and the four contrasting examples from BR-581. No script classifies product vs architecture; `validate-add` stays structural and never claims architectural correctness.
2. **One projection command, no stored report.** `render-add` loads the ADD, runs the existing document validation with freshness, and prints Markdown to stdout. It writes no file, adds no state and cannot be approved or edited; re-running after any ADD edit reflects the new content.
3. **State is derived, never asserted.** Mapping, in this order: structural errors other than a stale approval digest -> command fails non-zero naming the errors (no degraded rendering); `approved` true with matching digest and `fresh` -> «утверждён»; `approved` true with stale digest or freshness not `fresh` -> «требует актуализации»; any open choice or unresolved contradiction -> «нужны решения»; no elements and no open choice -> «предложение»; otherwise -> «готов к утверждению» when freshness is proven, else «требует актуализации»; an approved ADD whose digest is stale is treated as unapproved for rendering so that open choices added after approval cannot turn the state into a validation failure. Header carries BR reference (required `--requirement`), `target_repository`, the add id and the content digest prefix as revision identity.
4. **Compatible optional fields.** Element: `current`, `rationale`, `impact`, `refs` (strings). Choice: `kind` (`architecture` default meaning existing entries; `product` means a clarification of the BR), `options` (list of `{label, tradeoffs}`), `recommendation`. Absent means the column/line is omitted; an invalid type fails `validate-add`. They sit inside the existing digest, so changing them invalidates approval by the existing rule. `ADD_SCHEMA_VERSION` is unchanged because old documents stay valid and render.
5. **Product questions are separate.** A `kind: product` open choice renders under its own heading "Уточнение Business Requirement" and still blocks approval through the existing open-choice rule; the guidance tells the agent to return it to the BR instead of deciding it in the ADD.
6. **Fixed Russian structure, proportional.** Sections in order: header/state; «Итог» from `requirement.summary` (agent-authored, 2–4 sentences, required for the render of a non-empty ADD or the command fails); «Существенные изменения» table over `new`/`changed` elements; «Что сохраняется» from `preserved` elements and `reused_constraints`; «Вопросы к человеку» only when choices exist; «Риски и следующий шаг» from open assumptions/contradictions plus a single action line chosen by state. Empty sections are omitted. The labels are static text in the script, so the shape is identical for every agent and project.
7. **Wiring.** The capability Markdown tells the agent to present an ADD to the human by running `render-add` and relaying its output, adding nothing that contradicts it. `agent-workflow.md`, `engineering-capabilities.md` and the `AGENTS.md` concern row link to it instead of restating it. Presentation adds no stop: the existing single checkpoint remains the only human pause.
8. **Verification without overclaiming.** Deterministic tests render representative ADD fixtures (detailed-BR with only real deltas, API/event contract delta, reused existing contract, open architectural alternative with options/recommendation, product clarification, stale approval after edit, empty/no-ADD path) and assert structure and state from behaviour, plus determinism across two invocations. The guidance cases are carried in the eval fixture with objective verifiers over the text and are stated as a pinned standard, not proof of live agent judgement. Live multi-agent behaviour is not claimed; a Copier render proves an operator-managed and a portable project receive the file, and the first real material-design Requirement after release is observed in its retrospective.

## Risks

- The agent may still overfill the ADD. Mitigation: concrete test question and examples, summary-first rendering that makes a BR retelling visible, and no pretence that tooling proves correctness.
- Optional fields could grow into a mandatory template. Mitigation: absence only shortens output; tests pin that no field is required.
- Russian labels in code could drift from the guidance. Mitigation: a test asserts the guidance names the same sections.
