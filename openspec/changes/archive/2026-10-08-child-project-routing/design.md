## Context

Current behavior, verified in code:

- `requirement_intake.materialize_handoff` fetches the parent (`fetch_issue`), checks only `type:requirement`, derives `canonical_requirement_context` (target repository from the body), then calls `managed_task.authoring_config(root)`. That config comes from the checkout's `.dev-platform.toml` `[development_backlog]` (`repository`, `project_label`, `default_priority`).
- The only routing comparison is `managed_task.origin_repository(root) != report["target_repository"]` (checkout vs pre-authoring target). Nothing compares `config.repository` with the Requirement's repository, and nothing compares `config.project_label` with the parent's `project:*` label.
- `managed_task.create_task` -> `validate_backlog_labels` only proves the checkout's labels exist on `config.repository`; `create_issue` applies `config.project_label`; `verify_published_managed_task` then proves the child has exactly `config.project_label`. This is circular: the child is checked against the configuration that produced it.
- For a reused exact-handoff candidate, `materialize_handoff` validates the package content only; labels are not examined at all.
- `link_child` rejects a child outside `repository` only after the child exists (`child_repository != repository`), adds `type:internal-change` via `gh issue edit --add-label` and never reads that label back; the final readback checks body identity and the `Requirement:` back-reference. `materialize_handoff` then rechecks only the checklist entry and back-reference.
- Contrast: `create_requirement` -> `_reconcile_requirement_labels` and `requirement_label_problems` already implement exact expected-label proof with conflict-vs-missing separation for Requirements; `repair_authoring_labels` completes only missing labels and refuses conflicting ones. Children have no equivalent against the parent.

Defect: a checkout whose configured `project_label` differs from the Requirement's `project:*` label produces a child routed to the wrong project, reported as success.

## Goals

- Child routing is derived from the exact parent Requirement and the committed target configuration, and they must agree.
- Contradictions are rejected before any Issue is created.
- Success is reported only after read-back proves `project:*`, `type:internal-change` and parent link.
- Existing contradictory children are visible errors, not silent relabels.

## Decisions

1. **Authoritative sources.** The expected project label is the single `project:*` label on the parent Requirement as read from GitHub in this invocation (`managed_task.issue_labels(parent)`). The Backlog repository is the Requirement's repository. The committed target configuration is `managed_task.authoring_config(root)`. A new pure helper `resolve_child_routing(parent_issue, requirement_ref, config)` returns `{"project_label", "repository"}` or raises `RequirementIntakeError`. It fails explicitly when: the parent has zero or more than one `project:*` label (names the labels found); `config.repository != requirement repository`; `config.project_label.lower() != parent project label`. Messages name Requirement, expected and found values. No default, no "prefer the config" or "prefer the parent" choice: disagreement is an error. It reuses the existing label vocabulary and does not duplicate `requirement_label_problems`.
2. **Reject before publication.** `materialize_handoff` calls `resolve_child_routing` immediately after the `type:requirement` check and before `create_task`, and before any candidate search, so neither creation nor linkage of a misrouted child can start. Missing configuration keeps raising `ManagedTaskError` from `authoring_config`, wrapped as `RequirementIntakeError` naming the missing input; the label's existence on the Backlog is still proven by the existing `validate_backlog_labels`, whose missing-label error is propagated unchanged.
3. **Read-back proof.** A helper `verify_child_routing(child_issue, child_ref, routing, requirement_ref)` checks, from a fresh `fetch_issue`: `project:*` label set equals exactly `{expected}`; `type:internal-change` present; open Issue (not a PR) in `routing.repository`; body contains the `Requirement: <ref>` back-reference. Combined with the existing check that the parent checklist lists the child, `materialize_handoff` returns success only after it. It runs after `link_child` for both the created and the reused-child path, so a retry of an interrupted materialization re-proves everything.
4. **Existing mislabeled child.** For a reused candidate, `verify_child_routing` runs before `link_child` as well: a conflicting `project:*` label raises an error naming the child, expected and found labels, with guidance to correct the label on the Backlog (or close the child and retry) manually. The platform never removes or replaces a `project:*` label. The only idempotent repair on retry is adding a missing `type:internal-change` through the existing `link_child`, followed by re-verification; a missing expected `project:*` label on a child whose labels contain no `project:*` at all is likewise reported as an error with guidance, not added, because the child's provenance route was not validated (explicitly: no silent repair beyond the single deterministic `type:internal-change` addition already shipped).
5. **link_child read-back.** After `gh issue edit --add-label`, `link_child` fetches the child and fails if `type:internal-change` is absent, so the standalone `link-child` command is as strict as materialization. It also rejects a child whose `project:*` label contradicts the parent's before editing anything, using the same pure label comparison (parent labels read once, child labels from the already fetched child). The existing same-repository check stays.
6. **Template parity.** The implementation lives in `template/scripts/requirement_intake.py`; `scripts/requirement_intake.py` is a shim, so no second copy exists. Generated downstream projects ship the same code through the template; downstream Requirement support still gated by `requirement_target_lifecycle.require_local_target_support`.
7. **No fallbacks.** No derived default label, no retry that picks the other source, no catch-and-continue around label reads; GitHub or payload errors propagate as the existing named errors.

## Risks

- Existing Requirements created before label enforcement may have no or multiple `project:*` labels; they now fail loudly. This is intended; repair is a manual label fix on the Requirement.
- Case differences: comparison is lowercase, as `issue_labels` already lowercases.
- The extra `fetch_issue` calls add latency of a few API requests per materialization; acceptable against correctness.

## Verification

Unit tests in `tests/test_requirement_intake.py` with patched `fetch_issue`/`run`/`create_task`: consistent routing succeeds and returns the verified result; config label differing from parent label raises and `create_task` is not called; config repository differing from the Requirement repository raises before creation; parent with zero or two `project:*` labels raises; read-back after create lacking `project:*` or `type:internal-change` or back-reference raises and no success payload is produced; reused child with a conflicting project label raises without any label mutation command (assert no `--add-label`/`--remove-label`/labels API call); reused child lacking only `type:internal-change` is completed once and re-verified; standalone `link_child` with contradictory child label raises before `gh issue edit`, and a label write that does not read back raises. A `tests/test_managed_task.py` case confirms `create_task` behavior is unchanged for direct managed tasks. Source and template consistency come from the standard `run_test_groups.py --all` checks. verification.md records actual commands and limitations; real lifecycle dogfood remains the parent release prerequisite.
