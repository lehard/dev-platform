## Context

- `template/scripts/lifecycle_workers.py` already owns the contract: head-bound jobs, claim/result comments, `work-next --kinds ... --repo ... --run`, per-PR and per-provider selection, a bounded provider readiness probe (`provider_readiness`), a credential-free child environment (`credential_free_env`, which drops `GH*`/`GITHUB*` credentials and keeps the provider's own key), a scratch HOME, and the harness-only expected-head push. Review is read-only through the platform-launched headless `claude -p` runner with a before/after workspace check.
- Trust: claim and result comments are accepted from the configured coordinator App (`[publication] coordinator_app`) and from proven repository writers. A worker that uses the same App needs no change to trust.
- `publication-queue.yml` is the only workflow that holds the App token. It runs default-branch code on `pull_request_target[labeled]`, a 5-minute schedule and dispatch, with one concurrency group, and never checks out PR content while holding the token.
- Provider credentials reach the Claude process only as an environment variable (`CLAUDE_CODE_OAUTH_TOKEN`), which the scratch environment keeps; no login file is needed on a runner.

## Decisions

1. **Reuse the worker, add only a placement.** The workflow runs the existing command. No new queue, marker, state store or job kind. Hosted differs from local only in where it runs and which kinds it advertises (the existing placement rule).
2. **Trusted code only.** Every trigger executes the default branch (`actions/checkout` of the default ref, `fetch-depth: 0`, source contract installed from `dev-platform/source-contract.toml` exactly as the queue workflow does). The change ships `workflow_dispatch` only. Automatic triggers — `workflow_run` of the publication queue workflow (completed) and a 10-minute `schedule` safety net — are added by the owner in a separate reviewed change when enabling the pilot; the document names them and the structure tests pin the allowed set (`workflow_dispatch`, `workflow_run` of the queue, `schedule`). No `pull_request` trigger and no checkout of a PR ref by any workflow step. The PR head is fetched only by the harness into a disposable credential-free checkout.
3. **Required configuration, no silent off-switch.** Repository variable `DEV_PLATFORM_HOSTED_KINDS` (comma list drawn from `review,repair,finalize,integration-repair,retrospective,terminal-reconciliation,cleanup`) is required configuration: when the workflow runs and it is unset or empty, the `plan` job fails explicitly naming the variable, and no class job runs. Being off is the absence of automatic triggers, not an empty variable. A value that names an unknown kind, or a kind outside the proven classes, fails the `plan` job naming the kind.
4. **Class-scoped tokens.** The `plan` job holds no token. Each class job runs `actions/create-github-app-token` (same pinned action and App as the queue) limited to the current repository and to its class rights: both hosted classes — pull-requests write (claim/result comments) and contents write, because the harness pushes the review evidence commit (`review`) or the finalization commit (`finalize`) to the candidate branch with an expected-head guard. The classes differ in kinds, provider need, runner tooling and concurrency group, not in rights; a future read-only class would get contents read. Workflow-level `permissions: contents: read`; no `workflows`, `administration`, `actions` or `id-token` scope. The hosted worker issues no merge request; merging stays with the publication queue and its expected-head guard.
5. **Credential boundary by construction and by probe.** The worker process holds the App token in `GH_TOKEN`; every LLM, project-check and harness-child process is started through the existing credential-free environment and scratch HOME. The preflight proves it on the runner: it runs a child through that environment and requires that no GitHub/App variable, askpass helper, SSH agent or credential-helper configuration is visible. The provider secret is passed to the LLM only as the provider's own variable. The workflow never echoes secrets and never passes secret values to the preflight (presence flags only, as in the queue workflow).
6. **Hosted preflight is a repository-owned entrypoint.** `lifecycle_workers.py hosted-preflight --mode ci --class <review|branch|post-merge> --repo owner/repo`: (a) the class and requested kinds are valid and the class's kinds are the enabled subset; (b) the provider secret presence flag is set; (c) `claude` is installed and passes `provider_readiness` in the scratch environment — the same probe a job would use; (d) the credential-boundary probe above; (e) the token is an installation token scoped to exactly this repository (the existing queue probe; GitHub exposes no readable permission set, so the class's rights are those requested at mint, pinned by the workflow structure tests). It stops at the first failure, exits non-zero with a diagnostic naming the input or category, prints no credential value, and substitutes nothing. A class that fails is not run; the failure is the evidence recorded for that kind.
7. **Only kinds with a hosted-capable executor are hosted.** `review` needs the read-only Claude runner and `finalize` needs a checkout, the project checks and the harness push — both run from a credential-free scratch environment on a runner. `repair` and `integration-repair` need a platform-supported headless writer with proven containment (a writer holds a shell and the provider token); that contract is BR-576's and is not changed here, so the preflight refuses these kinds naming BR-576. `retrospective`, `terminal-reconciliation` and `cleanup` read machine-local lifecycle state (friction log, retrospective checkpoints) and Development Backlog Issues/Project that the runner token cannot reach, so they are refused naming the local operator node. Refusal is a named failure of the plan/preflight, never a silent skip; these kinds remain on the local operator node (BR-433) and the pilot slice may lift a refusal when its blocker is removed.
8. **Concrete outcomes.** The worker already prints one JSON result (`idle`, `claimed` with its execution outcome, provider `unavailable` with the limitation) and exits 2 on `WorkerError`. The workflow writes that result to the job summary under a fixed heading and lets the exit code decide the run conclusion: unavailable provider, auth, network and `gh` failures end the run red with the cause. An idle or claimed-and-resulted run is green and says only that — it never says the candidate or Requirement is done. Retry is the existing bounded job retry/blocked-escalation path, not a workflow loop.
9. **Duplicate and restart safety is inherited, then pinned.** One concurrency group per class (`cancel-in-progress: false`) serialises hosted runs; the job `timeout-minutes` is below the claim TTL, so a live run is never reclaimed and a dead one is reclaimable after the TTL. Worker identity is `gha-<run_id>-<run_attempt>-<class>` through `DEV_PLATFORM_WORKER` (it satisfies the identity pattern and is unique per attempt). A re-delivered event, a re-run, a moved PR head or an advanced `main` are handled by the existing head-bound claim/result and discard rules; the change adds tests, not a mechanism.
10. **Enablement is the owner's step; the pilot is the next slice.** An agent never enters credentials. `docs/engineering/hosted-lifecycle-workers.md` tells the owner, in order: create a dedicated, revocable, usage-capped provider token and store it as the repository secret; set the App variables if absent and `DEV_PLATFORM_HOSTED_KINDS` (start with `review`); run the workflow by hand and read the preflight outcome; only then add the `workflow_run` and `schedule` triggers through a normal reviewed change; rollback is removing the triggers (and, if needed, clearing the variable, which makes any manual run fail explicitly). The document also lists the constraints the pilot must verify per kind (runtime and credential availability, credential-boundary proof, token scope, duration, cost and limits, failure behavior) and the rule that an unprovable kind stays off the hosted path with BR-433 as its recorded basis. The real-PR pilot and the decision record are the next BR-610 slice.

## Risks and mitigations

- **Provider token on a runner.** A hosted LLM process holds a long-lived provider credential. Mitigation: dedicated, revocable, usage-capped token for this repository only; only same-repository branches of trusted writers are eligible (existing trust model); review uses the runtime-enforced read-only tool allowlist; repair is not hosted in this slice; the secret is never in the plan job, in preflight arguments or in outputs.
- **PR-controlled code meets an App token.** The worker only fetches PR content into the harness's disposable credential-free checkout; project checks run in the credential-free check environment; the workflow tests assert no step checks out or runs PR content in a job that holds a token.
- **Duplicate execution or stale result.** Inherited head-bound claim/discard; concurrency group; timeout below TTL; unique identities. Tests exercise overlapping invocations, an expired claim, a moved head and an advanced `main`.
- **Cost and hang.** Idle runs exit without a provider call; job timeout bounds a run; the 10-minute schedule is a backstop behind the event trigger; there are no automatic triggers until the owner adds them. Observed durations and limits are part of the pilot slice's record.
- **Unprovable prerequisite.** Treated as a valid outcome: the kind is not enabled, the limitation is reported by the preflight, the local node (BR-433) is the named basis — never a silent downgrade.
- **Permission breadth.** `pull-requests: write` could technically merge. The hosted code path issues no merge; a test records that no merge request is made; branch protection and the queue's guard are unchanged.
