## Context

`candidate_lifecycle.post_merge_job` derives the next post-merge obligation of a merged candidate purely from trusted result receipts: for each kind (retrospective, terminal-reconciliation, cleanup) attempts `a0..a2` are tried in order; an outcome starting `failed`/`blocked` moves to the next attempt, any other completes the kind, three failed ones exhaust it. Job ids are `pr{N}:{kind}:{head}:a{attempt}` and already support a `:r{seq}` re-offer suffix (used for review/repair/finalize re-offers). `integration_contour.run_claimed_post_merge` turns `JobBlocked` into a `blocked:` receipt and any other exception into `failed:`. `local_cleanup` returns `already-clean` when no worktree of the branch exists.

## Decisions

- **Pacing in the runner, not in derivation.** The runner already owns rounds (`START_INTERVAL_SECONDS` = 600). After a `work-next` run whose `execution.status` is `blocked` or `failed`, the runner adds that PR to a per-round exclusion set passed to every further `work-next` as `--exclude-pr`. This gives at most one attempt per obligation per round and therefore at least one start interval between attempts, with no wall-clock state in the pure derivation. `work_next`/`select_job` gain an `exclude_prs` filter beside `only_prs`. Rejected: a minimum interval derived from receipt timestamps (time-dependent derivation, another policy constant, and it would also affect the coordinator's own runs).
- **Environment defect is not an obligation outcome.** `integration_contour.PostMergeEnvironmentError` (a `WorkerError`) is raised by `run_cleanup` when any cleanup error is `process-check-unavailable`; `run_claimed_post_merge` re-raises it instead of mapping it to a receipt. `work-next` then releases the claim (released results are never outcomes) and exits 2; the runner fails the round with the message. The runner also checks `shutil.which("lsof")` with its own PATH before the first claim and fails the round naming the tool, so the known defect never claims. `active-board`, dirty or identity-mismatch refusals stay `blocked` obligation outcomes.
- **Re-offer as an appended coordinator record.** `pr_review_gate.reoffer_post_merge` (CLI `publication_queue.py reoffer-post-merge`) requires reason, actor (authenticated `gh` login, as `resume`) and `--expected-head`; refuses before any write when the PR is not merged, the merged head differs, there is no coordinator record at the merged head, the obligation is not exhausted, or a live claim holds one of its jobs. It publishes `_transition(..., "merged", head, set_attempts={"post-merge-reoffers": seq}, next_job=job_record(kind, head, identity, 0, reoffer=event))` with `event = {seq, action, kind, reason, actor, via?, head, at}`. `job_record` accepts a re-offer for post-merge kinds.
- **Derivation with re-offers.** `post_merge_job` reads `attempts["post-merge-reoffers"]` (default absent = 0). With seq > 0 the record's `next_job.reoffer` must carry that seq (otherwise the record is malformed and derivation raises). A kind is complete when any trusted outcome of any attempt under any seq `0..seq` is not `failed`/`blocked`; otherwise attempts `a0..a2` are offered under the current seq's ids (`:r{seq}`), which gives the fresh budget. Exhaustion under the current seq again yields the existing `post-merge {kind} exhausted` reason and a new attention (attempt counters differ, so the attention key differs).
- **One eligibility function.** `pr_review_gate.post_merge_reoffer_plan(candidate, comments, trust, now)` returns the exhausted kind or raises `ReofferRefused`; the command, `lifecycle_overview` and `publication_queue.attention_body` use it, and print `python3 scripts/publication_queue.py reoffer-post-merge --pr N --expected-head <head> --via chat-coordinator --reason "<why>"`.

## Risks

- A wrong exclusion could starve a PR; it lasts only for the round and applies only after a blocked/failed run of that PR.
- A re-offer of cleanup while the cause persists spends the new budget at one attempt per round and posts a new attention; the operator is expected to fix the cause first.
- Records of merged PRs are new: derivation already reads exact-head records for merged PRs; malformed ones are skipped for merged PRs, so the re-offer record is validated by `validate_marker` before posting via `build_handoff_record`.
