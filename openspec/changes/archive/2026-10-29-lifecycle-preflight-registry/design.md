## Context

The cheap gates exist already: `enforce_scope_gate` (claim and overlap), `task_reconciliation.observe_candidate` (freshness, incl. behind-mergeable), `shared_workspace.preflight`/`audit` (permissions), `require_active_change_ready`, the private-reference guard, `refuse_repeated_run`. They are scattered: `select_checks.main` calls the scope gate only when the freshness branch applies; `finish` evaluates a consolidated blocker list but never the project's cheap test gates; the writer-guard baseline is a unit test inside `run_test_groups.py --all`.

## Decisions

- **One registry module, gate functions reused.** `lifecycle_preflight.CONDITIONS` is an ordered tuple of `Condition(id, gates, check)`. `check` receives a `PreflightContext` (root, integration root, branch, entry name, freshness mode) and returns a `ConditionResult(state, detail)` or raises the gate's own failure. The preflight catches the gate failure, keeps its message verbatim (it already carries the catalog class line and recovery) and adds the condition id. Conditions never reimplement a rule; the same-answer test calls the gate and the condition on one state and compares.
- **Conditions (in order):** `shared-workspace` (permissions; repairs own paths), `board-claim-and-scope` (`enforce_scope_gate`: covers `scope-gate-unavailable` and `scope-overlap`), `task-base` (freshness classification, keeping the `contribution-base`/`proven-base` modes and the behind-mergeable rule as the selector applies them today), `project-cheap-gates` (`preflight_commands`). The existing selector preflights (managed identity, active change ready, private lineage, repeated run) stay where they are and are listed in the printed output as already run before the registry; they are not moved, so their behavior and order are unchanged.
- **All refusals together.** Conditions are independent and cheap, so every violated one is collected and reported in one error (as `finish` does for its blockers), each with its repair command.
- **Explicit not-applicable.** A condition that does not apply (agent board capability off, declared disposable checkout, `harness_mode=project`, no `preflight_commands`) returns `not-applicable` with the configuration fact that makes it so. A condition that cannot be evaluated (unreadable board, missing config) is a refusal, never a pass.
- **Permissions: own paths repaired, foreign refused.** The condition audits without fixing, splits findings by `st_uid == geteuid()`, refuses first on any foreign-owned finding (the existing `format_admission_findings` text with owner and command), then runs the existing `shared_workspace.preflight(fix=True)` and reports the repaired paths. The mac/APFS setgid inheritance gap is handled by that repair, as it is in `finish` today. Multi-account behaviour remains BR-469.
- **Project cheap gates are configured, not hard-coded.** `[settings] preflight_commands` (list of shell commands, run from the root, any non-zero refuses naming the command and the diagnostic tail). The platform sets `python3 -m unittest tests.test_shared_writer_guard`; downstream projects without the key get `not-applicable (settings.preflight_commands not configured)`. The test remains in the full suite: the preflight runs the gate itself, not a copy of its rule.
- **Gate registry in the catalog.** `blocking-gates.toml` entries gain `preflight` (a condition id) or `no_preflight` (non-empty reason). `_platform_common`'s catalog validation requires exactly one. `tests/test_blocking_gates.py` checks every `preflight` id exists in `CONDITIONS`, every condition's declared `gates` match catalog entries that name it, and that a `no_preflight` reason is not a placeholder (non-empty, at least a sentence). A new blocking gate must already be cataloged (existing scan); now the catalog entry cannot be written without the decision. Rejected: a separate registry file (a second source for the same gate list, can drift), and scanning source for `raise` sites (cannot tell blocking-after-run from at-entry).
- **Entry points.** `select_checks.main` calls `run_preflight(entry="select-checks")` at the start of `--execute`; `finish_task.main` runs it before the developer handoff and after the already-merged recovery returns, before `observe_completion_blockers`, so a first submission and a re-submission take the same path; the early permission step reports paths it repaired. The selector's inline scope block is replaced by the registry call; its inline freshness block stays, because it produces the `base_contract` evidence and handles the `--proven-base`/`--contribution-base` contracts, and the `task-base` condition is declared not applicable in those modes. The board condition keeps the applicability the selector's scope gate had (a run that starts the full validation set or produces coordinator handoff evidence); other selections declare it not applicable with that reason. On the non-handoff `finish` path `finish`'s consolidated blocker list keeps `task-freshness`/`scope-overlap` (same functions, reported together with its other blockers), so the preflight declares those two conditions evaluated there; the developer-handoff path runs them in the preflight. A project without a check-configuration file reports `project-cheap-gates` as not applicable with that fact. The pre-publication scope recheck in `finish` is untouched (race-sensitive).

## Risks

- A condition that wrongly refuses blocks the expensive command. Mitigation: each condition only wraps an existing gate function; tests cover pass, refuse and not-applicable per condition.
- A repaired path hides a recurring cause. Mitigation: the repair is printed every time with the path list.
- The preflight adds seconds to every run; the project command is one unit-test module (about a second).
- The template changes ship to managed projects through a release: `preflight_commands` is optional, the catalog fields are platform-owned.
