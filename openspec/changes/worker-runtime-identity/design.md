## Context

Verified against the current tree (`template/scripts/` is the implementation; `scripts/` holds shims).

Worker identity
- `lifecycle_workers.main` (`work-next` parser): `--worker` defaults to `os.environ.get("DEV_PLATFORM_WORKER", f"worker-{os.getpid()}")`. The identity has no host component and no per-launch component, so PID reuse after a restart and equal PIDs on two hosts collide. The value is never validated; `claim_body` and `result_body` write whatever string arrives.
- `i_won` and `winning_claim` decide ownership by `claim["worker"] == worker`, so a collision hands one worker another worker's claim.
- `execute_job`, `pr_review_gate.run_claimed`, `integration_contour.run_claimed_integration_repair` default `worker="worker"`, a constant. A caller that forgets the argument claims and reports as `worker` silently.

Repair provider
- `publication_queue.publish_job` (kinds `review`, `repair`) takes `providers` from `independent_review_runner.settings(root).get("providers")` or `resolve_provider(root, config)`. `resolve_provider` reads `model_routing.read_current_durable_route(root)`, which is the route of the checkout the code runs in. Developer-side `admit` (publishes the first review job) runs in the task checkout and sees the right route. Coordinator-side calls (`publish_job(..., "repair", ...)` for a failed `required-checks` repair, `integration-repair` publication in `publication_queue` and `integration_contour.run_claimed_integration_repair`) run in the coordinator checkout, where the route is another task's or absent.
- When resolution fails, `resolve_provider` returns `None` and `publish_job` substitutes `"unresolved-originating-task-route"`, emits friction `fallback ... falls back to the default provider`, and still publishes the job. `pr_review_gate.complete_review`, `run_claimed` and `offer` repeat the same literal as a default.
- `publish_job` and `build_job` for repair/integration-repair do not constrain provider at all, and `lifecycle_workers.execute_job` never compares `job["providers"]` with the executor behind `--llm-command`. `work_next` claims before any provider check. `candidate_lifecycle` recovery copies `provider`/`providers` from the previous `next_job`, so a wrong value is also persisted.
- Routes are stored as `.claude/model-routing/<change>.json` (`model_routing._record_path`, `_durable_record_path`), machine-local and keyed by change. A remote worker or a coordinator on another machine cannot read them, so the originating provider must travel in the authenticated handoff record rather than be re-read later.

Project runtime
- `requirement_integration._run_full_checks` builds `credential_free_env(dict(os.environ), <scratch dir>)` for every project `full_commands` entry (`_full_check_commands` reads `[settings].full_commands` of `dev-platform/checks.toml`). `credential_free_env` removes GitHub/publication credentials and `GIT_CONFIG_*`, then, when a home is given, repoints `HOME`, `XDG_*` and `GH_CONFIG_DIR` to an empty directory. Docker contexts and registry config, uv configuration and cache, and application credential files under the real HOME are therefore absent for project checks. Other ambient variables (PATH, DOCKER_HOST, application keys) are already forwarded; the failure is the HOME substitution, which is correct for LLM and harness Git but wrong for trusted project checks.
- The same builder serves LLM processes (`run_llm`, `scratch_home` plus `--llm-home-file` login files), harness Git (`harness_git`) and composition/finalization (`requirement_composition`, `post_review_finalization`). Only the project-check use is in scope.
- `tests/test_requirement_contribution_composition.py::test_composition_full_checks_use_credential_free_isolated_home` currently asserts the scratch HOME for project checks; it encodes the defect and is replaced.

## Goals

- One worker identity per run: unique across hosts, PID reuse and relaunch, validated when operator-supplied, identical in claim, result and printed evidence.
- A repair or integration-repair job runs only on a worker serving its single authorized provider (the originating task route's provider by default, or the provider named by a recorded operator re-offer), proven before the claim and visible in job, claim and result evidence.
- Trusted project checks get an explicit, reviewable runtime; LLM and harness Git do not.
- Every missing or contradictory input fails with a message naming it. No sentinel provider, no default identity constant, no silent substitute runtime.

## Decisions

### D1. Worker identity contract

`lifecycle_workers.resolve_worker_identity(explicit, environ, *, hostname, pid, nonce)` returns the single identity for a run.
- Precedence: `--worker` value, then `DEV_PLATFORM_WORKER` if the variable is present (an empty value is present and invalid), otherwise a generated identity. Generation is the contract for an unspecified identity, not a masked failure; an invalid explicit value is never replaced by a generated one.
- Format `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,63}$`. Violations raise `WorkerError("invalid worker identity ...")` and `main` exits 2 before any GitHub call.
- Generated form `worker-<host>-<pid>-<nonce>`: `<host>` is `socket.gethostname()` lower-cased with characters outside `[a-z0-9.-]` mapped to `-` and truncated to 24 characters, `<pid>` is `os.getpid()`, `<nonce>` is `secrets.token_hex(6)` drawn once per launch. An empty hostname raises; there is no `localhost` substitute. Total length is at most 56.
- `main` resolves once and passes the result to `work_next`, every executor and the printed JSON (`"worker"` key). `claim_body` and `result_body` call the same validator so no caller can write an unvalidated identity. `execute_job`, `run_claimed`, `run_claimed_integration_repair` and the other `worker="worker"` defaults lose the default and take a required keyword argument. Replay and `i_won` still compare exact strings, so claims written by earlier worker versions (`worker-1234`) keep their meaning; the validator applies to writing, never to reading third-party comments.
- Rejected: hostname plus PID only (still collides after PID reuse on one host); UUID only (not diagnosable by an operator); persisting identity in a state file (new mutable state, ambiguous across clones).

### D2. Originating route travels in the handoff record

- At `publication_queue.admit` with a developer handoff, the developer checkout resolves the originating route with a new read-only helper `model_routing.read_route_for_change(root, change)`: it loads the durable record for that change from the integration root, validates payload `change` equals the requested change, validates managed provenance exactly as `read_durable_route` does, and requires a provider in `model_routing.PROVIDERS`. Missing, unreadable, mismatched or unsupported evidence raises `RoutingError`, which `admit` surfaces as `QueueError("handoff cannot resolve the originating task route for <change>: ...")` before any admission comment is written.
- The resolved `{"provider", "profile", "change"}` is persisted as an additive `route` field of the handoff record through `_transition`/`build_handoff_record` and surfaced by `derive_candidate` as `candidate["route"]`. This is a field passthrough in `candidate_lifecycle.py`; it must not alter marker authentication or exact-head rules owned by the publication-observation child. The record is already trusted only from the configured App or proven writers, so a candidate branch cannot forge it.
- Requirement-composition and contribution identities (`pr_review_gate.task_identity`) carry their `change`; for requirement composition the route is that of the composing task. A handoff whose identity has no `change` cannot name a route and fails at admission when it will offer repair-capable jobs.
- Later records inherit `route` from the previous exact-head record of the same candidate; a transition that changes `task_identity.change` to another change without a matching handoff `route` is contradictory and raises. Head changes alone keep the route.
- Rejected: reading `.claude/model-routing` in the coordinator (not available to remote coordinators, and it resolves the coordinator's own task, which is the present defect); putting the provider into `task_identity` (it is compared for gate reuse and would invalidate gates on a route correction).

### D3. Job provider resolution and the sentinel

- `publish_job` for kinds `repair` and `integration-repair` ignores `[independent_review]` configuration and sets `providers=[candidate["route"]["provider"]]`. No `route` on the current exact-head record raises `QueueError("<kind> job has no originating task route; re-run developer handoff")`. A caller-supplied `providers` that is not exactly that list raises as contradictory.
- For `review`, an explicit `[independent_review] providers` list keeps its documented ordered-fallback meaning (it is an operator decision); otherwise the provider is the recorded route, and absence raises. `resolve_provider` stays in use only for the local review/preflight path that runs inside the task checkout.
- The literal `unresolved-originating-task-route`, the `fallback` friction emission in `publish_job` and the sentinel defaults in `pr_review_gate.offer/complete_review/run_claimed` are deleted. A job whose `providers` contains an unknown name, is empty, or has `provider` contradicting `providers` is rejected by `build_job`'s consumer in `select_job` with a `WorkerError` naming the PR, never skipped silently.
- Amendment (operator provider switching, BR-439 compatibility): the recorded originating route provider is the default repair provider, but an explicit recorded operator re-offer authorizes another one. `lifecycle_workers.authorized_repair_providers(route, providers, reoffer, where)` accepts a job only when it names exactly one provider and that provider equals the route provider, or the job's `reoffer` record (`job_record(..., reoffer=...)`, shape `{"seq", "action", "from", "to", ...}` written by `publication_queue.py switch-provider` / `pr_review_gate.reoffer`) has `action` `switch-provider` and `to` equal to the job's providers. An unavailable-runtime retry (`action` `retry-unavailable`, `from == to`) repeats a list a prior validated record already carried and is accepted on the same `to` rule. Any other combination (no re-offer, re-offer naming another provider, `resume`, several providers) raises. `publish_job` takes an optional `reoffer` and applies the same check; `select_job` applies it per candidate using `candidate["route"]` before offering the job. Repair jobs still run on exactly one provider, and the switch stays visible because the re-offer event is part of the job record and its id.
  - Rationale: the user wants painless operator switching of an open candidate's provider (for example when one provider is out of quota). The operator event is an authenticated coordinator record, so it is an explicit decision and not a fallback; nothing switches providers automatically. Rejected: keeping route-only authorization (would make `switch-provider` unusable for repair); letting any worker with a different provider run the job (silent substitution).
- Coordinator-side repair publication (`required-checks` repair, `integration-repair` in `integration_contour` and `publication_queue`) now inherits from the candidate record and therefore works from any checkout.
- How the failing PR is surfaced by the coordinator sweep follows the existing `QueueError` handling around those call sites (recorded in the sweep's skipped/blocked diagnostics); implementation must verify each call site propagates rather than swallows, and add the missing propagation where one catches broadly.

### D4. Provider authorization before claiming

- `work-next` gains `--provider {codex,claude}`: the executor runtime behind `--llm-command`. It is required when `--kinds` includes `repair` or `integration-repair` and `--run` or a real claim is requested; omission raises `WorkerError("--provider is required for repair kinds")`. Kinds without writer executors do not need it.
- `select_job` takes `executor_provider`. For repair kinds it validates the job's providers (D3) and offers the job only when the worker provider equals the single recorded provider. A job for another provider is not claimable by this worker; `work_next` reports `{"status": "idle", "job": None, "unauthorized": [{"number", "kind", "required_provider"}]}` so an operator sees why nothing was claimed. This is routing of work to capable workers, not a degraded mode: the job remains offered for a matching worker and no worker ever runs it under another provider.
- `claim_body` and `result_body` carry an optional `provider` field; repair executors (`pr_review_gate.run_claimed`, `integration_contour.run_claimed_integration_repair`) re-verify before running that the worker provider equals the job provider and write it into the result. `--provider` is a worker declaration; the harness cannot prove which binary `--llm-command` runs. That residual trust is stated, not hidden, and the recorded provider makes a wrong declaration auditable.

### D5. Purpose-specific project check environment

Three explicit environment purposes live in `lifecycle_workers.py`: `llm` (`run_llm`, unchanged), `harness-git` (`harness_git`, `harness_push_env`, unchanged) and new `project-check`.

- Declaration, committed and reviewed: optional `[runtime]` table in `dev-platform/checks.toml` (read by `requirement_integration._full_check_commands`'s sibling `_project_runtime`):
  - `required_tools = ["docker", "uv"]`: each must resolve with `shutil.which` against the check environment's `PATH`.
  - `required_env = ["AI_ASSIST_DATABASE_URL"]`: each must be present and non-empty in the launching environment.
  - `home_paths = [".docker", ".config/uv", ".cache/uv"]`: relative paths under the operator's real HOME the checks need.
  Unknown keys, non-list values or non-string entries raise `RequirementIntegrationError`. Absence of `[runtime]` means no declared needs and today's isolated environment.
- Grant, machine-local, never in the candidate checkout: `home_paths` expose operator files, so they require an operator grant. `DEV_PLATFORM_PROJECT_RUNTIME_FILE` names an absolute TOML file with `allow_home_paths = [...]`. The file must exist, be outside the checkout being checked, and parse; every declared home path must be listed in the grant. Any declared home path without a grant, an unset variable while home paths are declared, or a grant file inside the checkout raises. Declaring only tools and env needs no grant file.
- Always refused, regardless of declaration or grant: names matching the GitHub/publication credential rules (`CREDENTIAL_VARS`, the `_CREDENTIAL_PATTERN` rule) in `required_env`, and home paths `.ssh`, `.config/gh`, `.gnupg`, `.netrc`, `.git-credentials`, `.git-credential`, absolute paths and `..` components.
- Construction `project_check_env(environ, scratch_home, runtime, source_home)`: start from `credential_free_env(environ, scratch_home)` (GitHub/publication credentials, `GIT_CONFIG_*`, askpass and the SSH agent stay removed; Git terminal prompt stays off), keep the scratch HOME, `XDG_*` and `GH_CONFIG_DIR`, and symlink each granted home path into the scratch HOME at its relative location so tools see their configuration and caches without exposing the rest of HOME. Every `required_env` name is verified present after scrubbing; every `required_tools` entry is verified on PATH. Failures raise `RequirementIntegrationError("project check runtime requires <kind> <name>: <reason>")` before the first command runs, once, not per command.
- `_run_full_checks` builds this environment once and passes it to every `full_commands` entry. LLM, harness Git and finalization environments do not call it, so no secret reaches them.
- The existing broad forwarding of non-credential ambient variables to project checks is unchanged and reported as an existing characteristic, not extended.
- Rejected: a real HOME with only GitHub variables removed (exposes `~/.ssh`, `~/.config/gh` and every operator credential to candidate-controlled check code); per-variable allow-lists in the committed file alone (a candidate could widen its own access); silently dropping an unmet declaration (hides the same failure the Requirement is about).

## Risks

- A provider switch is limited to what a trusted coordinator record states; a forged re-offer needs the same write trust as any handoff record.
- Candidates admitted before this change have no `route`; repair for them fails explicitly until a developer handoff is repeated. Accepted; there is no safe automatic reconstruction.
- `candidate_lifecycle.py` is shared with publication-observation. The route field must be additive and rebased onto that child; if the two touch the same parse function, order the merges rather than redesign.
- `--provider` is declared by the worker. A mislabeled worker still runs the wrong binary; the recorded provider provides audit evidence only.
- Home path symlinks give check code write access to the granted directories (caches). The grant is operator-reviewed per path; credentials directories are refused categorically.
- Required worker-identity argument removes a default: any out-of-tree caller of `execute_job`/`run_claimed` breaks loudly, which is intended; in-tree callers and tests are updated.
